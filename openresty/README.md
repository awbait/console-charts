# openresty

Чарт разворачивает небольшой веб-сервер на OpenResty (nginx с Lua)
в namespace команды. Сервер обрабатывает список адресов: отдаёт готовые
ответы, выполняет обработчики на Lua и проксирует запросы в другие сервисы.
Он нужен, когда точке входа надо ответить статикой (`robots.txt`, настройки
мобильного приложения) или собрать один ответ из нескольких сервисов.

## Что создаёт чарт

| Секция      | Что создаётся                                              | Когда брать                                            |
|-------------|------------------------------------------------------------|--------------------------------------------------------|
| `servers[]` | `Deployment`, `Service` и `ConfigMap` с `nginx.conf` на элемент | Нужны готовые ответы, обработчик на Lua или проксирование по адресам |

Сервер доступен только внутри кластера, по имени своего `Service`. Снаружи
его открывает маршрут чарта `ingress-gateway`: правило с условием на путь
и сервисом назначения `Service` сервера.

## Куда ставится релиз

Все ресурсы создаются в namespace релиза. Обработчик на Lua обращается
к сервисам по их полным именам, поэтому namespace сервера и namespace
сервисов, которые он опрашивает, могут различаться.

## Теги окружения и проекта

Секция `identity` задаётся один раз на релиз. Из неё собираются имена ресурсов
и labels, по которым ресурсы потом находятся в кластере.

| Поле                | Что это                                                                       |
|---------------------|--------------------------------------------------------------------------------|
| `identity.instance` | Тег инстанса окружения. Обязателен, значение из таблицы ниже                    |
| `identity.cluster`  | Тег кластера окружения. Обязателен, значение из таблицы ниже                    |
| `identity.project`  | Тег проекта. Обязателен, до 9 символов: строчные латинские буквы, цифры и дефис |

Дефис в теге проекта не может быть первым или последним символом. При заказе
через портал тег проекта заполняется автоматически из команды заказа.

Пара тегов окружения:

| Окружение      | `identity.cluster` | `identity.instance` |
|----------------|--------------------|---------------------|
| Infra-dev-ecpk | `inf`              | `in`                |
| dev-ecpk       | `dev`              | `id`                |
| techsec-dev    | `tco`              | `ed`                |
| dev-common     | `dev`              | `ed`                |
| test-common    | `tst`              | `ed`                |
| global         | `gl`               | `pr`                |
| observability  | `obs`              | `pr`                |
| techsec        | `tcc`              | `pr`                |
| int-common     | `cmi`              | `pr`                |
| ML             | `ml`               | `pr`                |
| ext-common     | `cme`              | `pr`                |

Оба поля описаны в схеме значений перечислением, поэтому в форме портала они
выбираются из списка. Берите значения строкой таблицы: схема проверяет каждое
поле по отдельности и не поймает пару из разных окружений.

## Имена ресурсов

Имя каждого ресурса собирается из пяти частей:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

- `instance`, `cluster`, `project` берутся из секции `identity`;
- `kindShort` зависит от типа ресурса: `dp` для `Deployment`, `svc` для
  `Service`, `cm` для `ConfigMap`;
- `name` берётся из `servers[].name`: от 2 до 6 символов, строчные латинские
  буквы, цифры и дефис.

Три ресурса одного сервера различаются только частью `kindShort`. Итоговое
имя обрезается до 63 символов. Примеры имён: `ed-dev-dp-nbox-static`,
`ed-dev-svc-nbox-static`, `ed-dev-cm-nbox-static`.

## Labels на ресурсах

Каждый ресурс чарта получает следующие метки:

| Label                          | Значение                                       |
|--------------------------------|------------------------------------------------|
| `app`                          | `openresty`. Не зависит от имени релиза.        |
| `app.kubernetes.io/name`       | Тег проекта из `identity.project`.             |
| `app.kubernetes.io/instance`   | Имя релиза.                                    |
| `app.kubernetes.io/component`  | Имя сервера из `servers[].name`.               |
| `app.kubernetes.io/managed-by` | `Helm`.                                        |
| `app.kubernetes.io/version`    | Версия OpenResty, под которую собран чарт.     |
| `helm.sh/chart`                | Имя и версия чарта.                            |
| `ecpk/instance`                | `identity.instance`, если тег задан.           |
| `ecpk/cluster`                 | `identity.cluster`, если тег задан.            |
| `ecpk/project`                 | `identity.project`, если тег задан.            |

Поды сервера несут те же метки. По `app.kubernetes.io/component` `Service`
выбирает поды своего сервера и никакие другие.

Добавьте свои метки через `generic.labels`, а аннотации через
`generic.annotations`. Они применяются ко всему релизу.

## Образ и DNS

Образ сервера это официальный OpenResty плюс библиотека `lua-resty-http`,
без которой обработчик на Lua не может обратиться к другому сервису.
Dockerfile лежит рядом с чартом в `docker/`. Собранный образ кладётся
в Harbor, и платформа указывает его в `image` при установке чарта: `registry`,
`repository`, `tag` и `pullPolicy`. Пустой `tag` означает `appVersion` чарта,
то есть версию OpenResty, под которую он собран. Секреты реестра
перечисляются в `imagePullSecrets`.

Обработчик на Lua разрешает имена сервисов через nginx, а не через систему,
поэтому в `dns.resolver` должен стоять DNS-сервер кластера: имя или адрес,
несколько через пробел. По умолчанию `kube-dns.kube-system.svc.cluster.local`.
Все эти поля в форме заказа скрыты.

## Секция `servers[]`

Добавьте элемент для каждого сервера. Для него создаются `Deployment`,
`Service` и `ConfigMap` с `nginx.conf`.

| Поле          | Нужно указать            | Что это                                                                 |
|---------------|--------------------------|--------------------------------------------------------------------------|
| `name`        | да                       | Имя сервера от 2 до 6 символов.                                          |
| `enabled`     | нет, по умолчанию `true` | При `false` ресурсы сервера не создаются.                                |
| `replicas`    | нет, по умолчанию `2`    | Сколько экземпляров работает одновременно. Экземпляры разводятся по разным нодам, когда планировщик может. |
| `port`        | нет, по умолчанию `80`   | Порт `Service`. Сам сервер слушает 8080.                                 |
| `resources`   | нет                      | Ресурсы контейнера. По умолчанию запрос 50m и 64Mi, предел 500m и 256Mi. |
| `locations[]` | да, хотя бы один         | Адреса, которые сервер обрабатывает. Их поля описаны ниже.               |

Сервер запускается не от root, с файловой системой только для чтения.
Изменение адресов перезапускает поды сервера по одному.

### Адреса `locations[]`

У каждого адреса есть путь, правило сравнения и ровно одно действие.

- `path`. Путь запроса, например `/robots.txt` или `/api`. Для правил
  `exact` и `prefix` он начинается с `/` и не содержит пробелов, кавычек,
  фигурных скобок и точек с запятой. Для `regex` это регулярное выражение
  nginx, как есть: чарт экранирует его для конфига сам.
- `match`. Как сравнивать путь запроса с указанным: `exact`, путь целиком
  (по умолчанию), `prefix`, начинается с указанного, или `regex`.
  Порядок выбора тот же, что у nginx: точное совпадение, затем самый
  длинный префикс, затем регулярные выражения в порядке перечисления.
- Действие, одно из трёх:
  - `response`. Готовый ответ: `status` (по умолчанию 200), `contentType`
    (по умолчанию `text/plain`), `body` и `headers`, дополнительные
    заголовки ответа. Тело отдаётся как есть: nginx не подставляет в него
    переменные, знак доллара безопасен.
  - `lua`. Тело `content_by_lua_block` из OpenResty: код выполняется
    на каждый запрос и сам формирует ответ. Доступны `resty.http` и `cjson`.
  - `proxyPass`. Адрес сервиса, куда передать запрос, `http://` или
    `https://`. Заголовки `Host`, `X-Real-IP`, `X-Forwarded-For`
    и `X-Forwarded-Proto` передаются дальше.

Путь `/healthz` занят: там сервер отвечает на проверки пода.

Пример с готовым ответом, обработчиком на Lua и проксированием, повторяющий
server-snippet приложения Visiology, лежит в `values.full.yaml`.

## Когда рендер останавливается

Чарт проверяет значения перед созданием ресурсов. Если конфигурация
неполная или содержит ошибку, рендер останавливается и указывает поле,
которое нужно исправить.

Рендер остановится в следующих случаях:

- Не заданы `identity.instance` или `identity.cluster` либо в них указаны
  недопустимые символы.
- Значение `identity.project` длиннее 9 символов или содержит недопустимые
  символы.
- Имя сервера короче 2 или длиннее 6 символов или содержит недопустимые
  символы.
- Не задан `image.repository` или `dns.resolver`, либо в `dns.resolver`
  что-то, кроме имён и адресов через пробел.
- У сервера пустой список `locations`, `replicas` меньше 1 или `port`
  вне диапазона от 1 до 65535.
- У адреса не задан `path`, в `match` значение, кроме `exact`, `prefix`
  и `regex`, или задано не ровно одно действие из `response`, `lua`
  и `proxyPass`.
- Путь адреса с правилом `exact` или `prefix` не начинается с `/` или
  содержит пробелы, кавычки, фигурные скобки или точки с запятой.
- Адрес с правилом `exact` занимает путь `/healthz`.
- В `response.status` не код HTTP от 100 до 599, в `response.contentType`
  не тип содержимого, в `response.headers` имя заголовка с недопустимыми
  символами.
- Поле `lua` пустое.
- В `proxyPass` не адрес `http://` или `https://`, либо в нём пробелы,
  кавычки, фигурные скобки или переменные nginx.

## Файлы чарта

| Файл                  | Для чего                                                                |
|-----------------------|--------------------------------------------------------------------------|
| `values.yaml`         | Значения по умолчанию. Список серверов пуст, ресурсы не создаются.        |
| `values.minimal.yaml` | Короткий рабочий пример: один сервер с `robots.txt` и проксированием.     |
| `values.full.yaml`    | Полный справочник параметров с пояснениями и примером для Visiology.     |
| `values.schema.json`  | Проверка значений при установке и форма заказа в портале.                |
| `view.schema.json`    | Настройки вида формы заказа и карточки сервиса в портале.                |
| `docker/Dockerfile`   | Сборка образа: официальный OpenResty плюс `lua-resty-http`.              |
