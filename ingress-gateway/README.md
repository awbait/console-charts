# ingress-gateway

Чарт создаёт точку входа для внешнего трафика на базе Istio и Kubernetes Gateway
API. Вы задаёте маршруты к сервисам команды, ограничения доступа, сертификаты
и при необходимости вход по единой учётной записи.

## Что создаёт чарт

Выберите нужные секции. Их можно использовать отдельно или вместе.

| Секция                | Что создаётся                                                              | Когда брать                                       |
|-----------------------|----------------------------------------------------------------------------|---------------------------------------------------|
| `gateways[]`          | `Gateway` и инфраструктурный `ConfigMap` на каждый элемент                  | Нужна точка входа в кластер                       |
| `xroutes[]`           | `HTTPRoute`, `GRPCRoute`, `TLSRoute`, `TCPRoute` или `UDPRoute`, а для ссылок на сервисы в другом namespace по умолчанию ещё и `ReferenceGrant` в namespace сервиса. Для сервисов с закреплением клиента ещё и `DestinationRule` (Istio) | Нужно направить трафик от точки входа к сервису   |
| `gateways[].proxy`    | `EnvoyFilter` (Istio) для подов точки входа                                | Нужны долгие запросы или большие заголовки        |
| `tls`                 | `Certificate` (cert-manager) для каждого слушателя, чей домен не описан в списке сертификатов, и `ExternalSecret` для каждого используемого сертификата из хранилища | Точка входа расшифровывает TLS |
| `policies`            | `NetworkPolicy` и `AuthorizationPolicy` (Istio) для подов каждой точки входа, а для сервисов в другом namespace ещё по одной в namespace сервиса | Нужно ограничить трафик точки входа и открыть ей доступ к сервисам |
| `oidcAuth`            | `HTTPRoute`, `ReferenceGrant`, две `AuthorizationPolicy` и `RequestAuthentication` | Нужен вход по единой учётной записи через Keycloak |

Секции связаны по именам. В `xroutes[].parentRefs[].gateway` укажите имя точки
входа из `gateways[].name`, а в `sectionName` укажите имя её слушателя из
`listeners[].name`.

## Куда ставится релиз

Все ресурсы создаются в namespace релиза. Ресурсы секции `oidcAuth` создаются
в namespace приложения, точки входа и oauth2-proxy. Эти три компонента вместе
обеспечивают вход по единой учётной записи.

## Теги окружения и проекта

Укажите теги в секции `identity` один раз для всего релиза. Они входят в имена
ресурсов и метки, по которым можно найти ресурсы в кластере.

| Поле                | Что это                                                                       |
|---------------------|--------------------------------------------------------------------------------|
| `identity.instance` | Тег инстанса окружения. Укажите значение из таблицы ниже. Поле обязательно.    |
| `identity.cluster`  | Тег кластера окружения. Укажите значение из таблицы ниже. Поле обязательно.    |
| `identity.project`  | Тег проекта. Поле обязательно. До 9 символов: строчные латинские буквы, цифры и дефис. |

Первый и последний символ тега проекта должны быть буквой или цифрой.

При заказе через портал тег проекта заполняется автоматически. Портал берёт
его из команды, от имени которой вы делаете заказ. Укажите тег самостоятельно,
если устанавливаете чарт напрямую.

Используйте пару тегов из строки нужного окружения:

| Окружение      | `identity.cluster` | `identity.instance` |
|----------------|--------------------|---------------------|
| Infra-dev-ecpk | `inf`              | `in`                |
| dev-ecpk       | `dev`              | `id`                |
| techsec-dev    | `tco`              | `ed`                |
| dev-common     | `dev`              | `ed`                |
| test-common    | `tst`              | `ed`                |
| global         | `gl`               | `pr`                |
| observability  | `obs`              | `pr`                |
| techsec        | `tcc`              | `pr`                |
| int-common     | `cmi`              | `pr`                |
| ML             | `ml`               | `pr`                |
| ext-common     | `cme`              | `pr`                |

В форме портала значения обоих полей выбираются из списка. Проверка значений
не проверяет их сочетание. Убедитесь, что оба тега относятся к одному
окружению.

## Имена ресурсов

Имя ресурса состоит из пяти частей:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

- `instance`, `cluster` и `project` берутся из секции `identity`.
- `kindShort` зависит от типа ресурса. Значения приведены в таблице ниже.
- `name` берётся из имени элемента секции. Используйте строчные латинские
  буквы, цифры и дефис. Для точки входа и слушателя допустимы имена от 2 до 9
  символов, для маршрута и сертификата из хранилища от 2 до 6 символов.

В имя маршрута и сертификата перед проектом добавляется имя точки входа:

```
{instance}-{cluster}-{kindShort}-{gateway}-{project}-{name}
```

Для маршрута имя точки входа берётся из первого элемента `parentRefs`.
Для сертификата используется имя точки входа, которой он нужен.

На разных точках входа можно использовать одинаковые имена маршрутов.
Например, `ed-dev-hr-edge-a-nbox-app` и `ed-dev-hr-edge-b-nbox-app` будут
разными ресурсами. Так же различаются имена секретов двух заказов в одном
namespace. На одной точке входа имена маршрутов одного типа должны быть
уникальны. При повторении имени рендер останавливается.

Если несколько слушателей одной точки входа используют один сертификат
из хранилища, он создаётся один раз. Для другой точки входа создаётся
отдельный секрет с сертификатом из той же записи хранилища.

Имя автоматически выпущенного сертификата включает имя слушателя:
`{instance}-{cluster}-cert-{gateway}-{project}-{listener}`.
Поэтому имена слушателей одной точки входа должны быть уникальны.
При повторении имени рендер останавливается.

| Тип ресурса           | `kindShort` | Тип ресурса | `kindShort` |
|-----------------------|-------------|-------------|-------------|
| `Gateway`             | `igw`       | `HTTPRoute` | `hr`        |
| `ConfigMap`           | `cm`        | `GRPCRoute` | `gr`        |
| `NetworkPolicy`       | `np`        | `TLSRoute`  | `tr`        |
| `AuthorizationPolicy` | `ap`        | `TCPRoute`  | `tcr`       |
| `Secret` (TLS)        | `secret`    | `UDPRoute`  | `ur`        |
| `ExternalSecret`      | `es`        | `Certificate` | `cert`    |
| `EnvoyFilter`         | `ef`        | `DestinationRule` | `dr`  |

Имя `ConfigMap` отличается от имени его `Gateway` только кодом `cm` вместо
`igw`. Итоговое имя обрезается до 63 символов. Примеры имён:
`ed-dev-igw-nbox-main`, `ed-dev-hr-edge-a-nbox-app`.

`EnvoyFilter` назван по точке входа, как её `Gateway`: `ed-dev-ef-nbox-main`.
`DestinationRule` назван по сервису, за которым закрепляют клиентов, а не по
элементу заказа: `{instance}-{cluster}-dr-{project}-{service}`, например
`ed-dev-dr-nbox-app`. Правило одно на сервис, сколько бы маршрутов к нему
ни вело.

Имена ресурсов для входа по единой учётной записи задайте вручную в секции
`oidcAuth`. Они не следуют этой схеме.

## Секция `gateways[]`

Добавьте элемент для каждой точки входа. Для него создаются `Gateway`
и инфраструктурный `ConfigMap`. Их имена различаются только частью
`kindShort`.

| Поле          | Нужно указать            | Что это                                                                     |
|---------------|--------------------------|------------------------------------------------------------------------------|
| `name`        | да                       | Имя точки входа от 2 до 9 символов. На него ссылаются маршруты.              |
| `enabled`     | нет, по умолчанию `true` | При `false` ресурсы `Gateway` и `ConfigMap` не создаются.                    |
| `ipAddress`   | нет                      | Постоянный адрес балансировщика. Передаётся в аннотацию MetalLB.             |
| `hpa`         | нет                      | Настройки автомасштабирования: `enabled`, `minReplicas`, `maxReplicas`, `averageUtilization`. |
| `resources`   | нет                      | Ресурсы контейнера `istio-proxy`.                                           |
| `proxy`       | нет                      | Настройки прокси точки входа: `streamIdleTimeout` и `maxRequestHeadersKb`. Описаны ниже. |
| `nodeSelector` | нет                     | Метки нод, на которых можно разместить под точки входа.                     |
| `tolerations` | нет                      | Допуски к ограничениям нод (taints). Укажите их в формате Kubernetes.        |
| `affinity`    | нет                      | Правила размещения пода: `nodeAffinity`, `podAffinity`, `podAntiAffinity`. Используйте формат Kubernetes. |
| `listeners[]` | да                       | Список слушателей. Их поля описаны ниже.                                    |

Внешний адрес точки входа объявляется в сеть с ноды, на которой размещён
её под. Если с этой ноды адрес не объявляется, точка входа работает внутри
кластера, но недоступна снаружи. Платформа может исключить такие ноды,
задав общие правила размещения в значениях своей установки. Эти правила
применяются ко всем точкам входа вашего заказа. Вам ничего дополнительно
настраивать не нужно, в том числе менять значения существующих заказов.

Блок `gatewayScheduling` содержит общие значения `nodeSelector`, `tolerations`
и `affinity` для всех точек входа заказа. В самом чарте этот блок по умолчанию
пуст. Правила в нём задаёт платформа. Используйте `nodeSelector`, чтобы выбрать
ноды по меткам, `tolerations`, чтобы разрешить размещение на нодах
с соответствующими ограничениями, и `affinity`, чтобы задать правила
размещения. Поля используют формат спецификации пода Kubernetes. Если задать
одно из этих полей в элементе `gateways[]`, оно целиком заменит одноимённое
правило платформы без слияния. Пустое значение отключает правило платформы
для этого поля у данной точки входа. Все эти поля скрыты в форме заказа.
При необходимости задайте их в values.

Блок `proxy` настраивает прокси точки входа там, где Gateway API полей
не даёт. Чарт создаёт `EnvoyFilter` для подов этой точки входа, и он
действует на все её слушатели. В форме заказа блок скрыт, в карточке заказа
он открывается пунктом «Редактировать прокси».

- `streamIdleTimeout`. Сколько точка входа ждёт следующих данных по запросу
  или ответу, прежде чем закрыть соединение. Без поля действует значение
  по умолчанию, 5 минут: запрос, который дольше молчит, обрывается.
  Укажите число секунд с суффиксом `s`, например `18000s`. Значение `0s`
  отключает ожидание. Это ограничение на паузу в передаче, а не на запрос
  целиком: для запроса целиком есть `timeouts` в правиле маршрута.
- `maxRequestHeadersKb`. Предельный суммарный размер заголовков одного
  запроса в килобайтах, от 1 до 8192. По умолчанию 60. Запрос с большими
  заголовками получает ошибку 431. Поднимите предел, если приложение
  присылает большие cookie или токены.

Если оба поля пусты, `EnvoyFilter` не создаётся.

Для каждого слушателя укажите:

- `name`. Имя слушателя от 2 до 9 символов. Маршрут ссылается на него
  через `sectionName`.
- `port` и `protocol`. Оба поля обязательны. Допустимые протоколы:
  `HTTP`, `HTTPS`, `TCP`, `UDP` и `TLS`.
- `hostname`. Домен обязателен для `HTTPS` и `TLS`. Для `TCP` и `UDP`
  поле скрыто в форме заказа. Даже если задать его в значениях чарта,
  оно не попадёт в `Gateway`.
- `tlsMode`. Используйте `Terminate` или `Passthrough`. Для `HTTPS`
  по умолчанию используется `Terminate`, для `TLS` используется `Passthrough`.
- `certificateRefs`. Укажите ссылки при `Terminate`, если сертификат уже
  есть в кластере под своим именем. Иначе он выбирается через секцию `tls`.
- `allowedRoutes`. Укажите, какие маршруты может принимать слушатель.

## Секция `tls` - сертификаты

Слушатель с `tlsMode: Terminate` расшифровывает трафик, поэтому ему нужен
сертификат для своего домена. Есть три способа получить сертификат.
По умолчанию он выпускается автоматически.

### Выпустить автоматически

Дополнительные поля заполнять не нужно. Чарт использует домен слушателя
и создаёт `Certificate`. Затем cert-manager получает сертификат
у платформенного издателя и сохраняет его в namespace релиза
как секрет `kubernetes.io/tls`.

Для каждого слушателя создаётся отдельный `Certificate`. Если два слушателя
используют один домен, каждый получит свой сертификат. Имя секрета зависит
от имени слушателя и не меняется при перестановке слушателей в списке.

Платформенный издатель может выпускать сертификаты только для разрешённых
доменов. Если ваш домен не разрешён, рендер остановится и укажет этот домен.
В таком случае добавьте сертификат одним из способов ниже. Настройки
издателя находятся в `tls.issuer` и скрыты в форме заказа.

### Взять из хранилища

Используйте этот способ, если сертификат и ключ находятся в хранилище
сертификатов Vault. Чарт создаст `ExternalSecret`. По нему External Secrets
Operator прочитает запись и будет поддерживать секрет `kubernetes.io/tls`
в namespace релиза.

В значениях заказа укажите путь к записи. Сертификат и приватный ключ
в репозиторий заказа не попадут.

| Поле          | Нужно указать | Что это                                                       |
|---------------|---------------|----------------------------------------------------------------|
| `source`      | нет           | Источник сертификата. По умолчанию `vault`.                    |
| `name`        | да            | Имя от 2 до 6 символов. Входит в имя секрета.                 |
| `domain`      | да            | Домен, который покрывает сертификат.                          |
| `path`        | да            | Путь к записи с сертификатом и ключом в Vault.                |
| `store`       | нет           | Имя `SecretStore`. Если не указать, используется `tls.store`. |
| `crtProperty` | нет           | Поле записи с сертификатом. По умолчанию `tls.crt`.           |
| `keyProperty` | нет           | Поле записи с приватным ключом. По умолчанию `tls.key`.        |

### Взять готовый секрет

Используйте этот способ, если сертификат уже добавлен в ваш namespace
как секрет `kubernetes.io/tls` без участия этого чарта. Чарт будет ссылаться
на готовый секрет и не создаст новый.

| Поле         | Нужно указать | Что это                                    |
|--------------|---------------|--------------------------------------------|
| `source`     | да            | Укажите `existing`.                        |
| `domain`     | да            | Домен, который покрывает сертификат.       |
| `secretName` | да            | Имя секрета в вашем namespace.             |

Поле `name` для такой записи не нужно. Имя готового секрета уже задано.

Сертификаты из хранилища и готовые секреты добавляйте в общий список
`tls.certificates`. Можно указать домены любого уровня, в том числе
за пределами `ecpk.test`.

### Из какого хранилища читается сертификат

Для доступа к хранилищу сертификатов используется `SecretStore`. Он должен
находиться в namespace релиза и обращаться к Vault от вашей роли.

Укажите имя хранилища сертификатов в поле `store` записи. Если поле
не заполнено, используется `tls.store`.

### Какой сертификат достанется точке входа

Для каждого слушателя чарт ищет сертификат по `hostname` в списке
`tls.certificates`. Используется первая подходящая запись сверху вниз.
Если подходящей записи нет, сертификат выпускается автоматически.

Ставьте запись с точным доменом перед записью со звёздочкой. Иначе более
общая запись может быть выбрана первой.

Домен со звёздочкой покрывает один уровень вложенности:

| Домен записи      | Покрывает                              | Не покрывает                          |
|-------------------|----------------------------------------|---------------------------------------|
| `*.idp.ecpk.test` | `app.idp.ecpk.test`, `*.idp.ecpk.test` | `idp.ecpk.test`, `a.str.idp.ecpk.test` |
| `*.str.idp.ecpk.test` | `a.str.idp.ecpk.test`              | `b.a.str.idp.ecpk.test`               |
| `shop.example.ru` | `shop.example.ru`                      | `www.shop.example.ru`                 |

Для более глубокого поддомена добавьте отдельную запись, если он выходит
за один уровень, покрытый сертификатом со звёздочкой. Например, запись
`*.idp.ecpk.test` не покрывает `a.str.idp.ecpk.test`.

Имена ресурсов для сертификата из хранилища включают `name` записи.
Для автоматически выпущенного сертификата используется имя слушателя.

| Ресурс           | Имя                                                         |
|------------------|--------------------------------------------------------------|
| `Secret`         | `{instance}-{cluster}-secret-{gateway}-{project}-{name}`      |
| `ExternalSecret` | `{instance}-{cluster}-es-{gateway}-{project}-{name}`          |
| `Certificate`    | `{instance}-{cluster}-cert-{gateway}-{project}-{listener}`    |
| `Secret` (автовыпуск) | `{instance}-{cluster}-secret-{gateway}-{project}-{listener}` |

На одной точке входа для сертификата из хранилища создаётся один
`ExternalSecret`, даже если сертификат используют несколько слушателей.
Для записей, которые не нужны ни одному слушателю, ресурсы не создаются.

Если сертификат уже есть в кластере и вы подключаете его напрямую,
укажите `certificateRefs` у слушателя. Тогда для этого слушателя
не создаются ни `ExternalSecret`, ни `Certificate`.

### Что происходит при удалении заказа

При удалении заказа `ExternalSecret` удаляется вместе со своим секретом.
Ресурс `Certificate` тоже удаляется, но выпущенный сертификат остаётся
в секрете в namespace. Новый заказ с тем же именем перезапишет этот секрет
при первом выпуске сертификата.

## Секция `xroutes[]`

| Поле           | Нужно указать                 | Что это                                                                 |
|----------------|-------------------------------|--------------------------------------------------------------------------|
| `name`         | да                            | Имя маршрута от 2 до 6 символов.                                         |
| `enabled`      | нет, по умолчанию `true`      | При `false` маршрут не создаётся.                                        |
| `kind`         | нет, по умолчанию `HTTPRoute` | Тип маршрута: `HTTPRoute`, `GRPCRoute`, `TLSRoute`, `TCPRoute` или `UDPRoute`. |
| `parentRefs[]` | да                            | В `gateway` укажите имя точки входа из `gateways[]`, в `sectionName` имя слушателя. |
| `hostnames[]`  | для HTTP, GRPC и TLS          | Домены маршрута. Для TLS используются имена SNI.                          |
| `rules[]`      | да                            | Правила маршрута. `backendRefs` обязателен, кроме правила с перенаправлением. `matches` и `filters` доступны только для HTTP и GRPC, `timeouts` только для HTTP. |

Правило с фильтром `RequestRedirect` точка входа обрабатывает сама: в нём
один такой фильтр, в его `requestRedirect` любой набор из `statusCode`,
`scheme`, `hostname`, `port` и `path`, а `backendRefs` и `URLRewrite`
в этом правиле не указываются.

В `backendRefs` укажите имя сервиса в поле `name` и его порт в поле `port`.
Поля `namespace`, `weight`, `sessionAffinity` и `h2UpgradePolicy`
необязательны.

В `timeouts` правила задаются ограничения времени для запросов, попавших
под это правило. Оба поля принимают длительность в формате Gateway API:
`30s`, `5m`, `1h30m`.

- `request`. Предельное время на запрос целиком, от получения запроса
  точкой входа до отправки полного ответа. После него клиент получает 504.
  Без поля ограничения нет.
- `backendRequest`. Предельное время одной попытки обращения к сервису.
  Не может быть больше `request`. Без поля действует `request`.

Ограничение на паузу в передаче данных задаётся не здесь, а в блоке `proxy`
точки входа, полем `streamIdleTimeout`.

В `sessionAffinity` у элемента `backendRefs[]` задаётся закрепление клиента
за экземпляром сервиса: все запросы с одной и той же cookie идут в один
и тот же под. Укажите `cookieName`, имя cookie, которую точка входа выдаёт
клиенту, и при необходимости `ttl`, срок её жизни числом секунд с суффиксом
`s`, например `172800s`. Без `ttl` cookie живёт до закрытия браузера.
Чарт создаёт `DestinationRule` в namespace релиза, видимую только точкам
входа этого релиза. Правило одно на сервис: оно действует на весь трафик
точки входа к этому сервису, из всех маршрутов и правил. Если два элемента
`backendRefs[]` называют один сервис с разными cookie или `ttl`, рендер
останавливается.

В `h2UpgradePolicy` у элемента `backendRefs[]` задаётся, переходит ли точка
входа на HTTP/2 в соединении с этим сервисом. Общее правило задаёт платформа
в настройках mesh, и если она переводит соединения на HTTP/2, сервис, который
HTTP/2 не понимает, отвечает ошибками или обрывает соединение. Значение
`DO_NOT_UPGRADE` оставляет такому сервису HTTP/1.1, `UPGRADE` переводит
на HTTP/2 принудительно. Без поля действует правило платформы. Настройка
уходит в ту же `DestinationRule`, что и закрепление клиента: правило одно
на сервис, и ссылки на один сервис могут дополнять друг друга, одна задаёт
cookie, другая протокол, но задать одну настройку по-разному нельзя.

Закрепление работает, потому что точка входа сама выбирает под сервиса.
Если у сервиса или его namespace стоит метка
`istio.io/ingress-use-waypoint: "true"`, трафик точки входа идёт через
waypoint, который балансирует сам, и закрепление перестаёт действовать.
Для таких сервисов `sessionAffinity` не поможет.

Если в `xroutes[].rules[].backendRefs[]` указан `namespace`, отличный от
namespace релиза, в котором развёрнута точка входа, чарт автоматически создаёт
`ReferenceGrant` в namespace сервиса. Он разрешает маршрутам ссылаться на
сервисы через границу namespace. Для ссылок в свой namespace разрешение не
требуется и не создаётся. На каждую пару «точка входа и namespace сервиса»
создаётся один `ReferenceGrant` с именем
`{instance}-{cluster}-rg-{gateway}-{project}-routes`, например
`id-dev-rg-dmd-dev-dmd-routes`. В разрешении перечислены только типы маршрутов
этой точки входа, которые ссылаются на этот namespace, и только указанные
в ссылках сервисы. Маршруты с `enabled: false` не учитываются.

Ничего дополнительно настраивать не нужно: `referenceGrant` по умолчанию
равен `true`, разрешение появляется вместе с маршрутом и удаляется вместе
с заказом. Если у вас нет прав создавать объекты в namespace сервиса,
укажите `referenceGrant: false` у соответствующего элемента `backendRefs[]`.
Тогда `ReferenceGrant` должны создать владельцы namespace сервиса, иначе
маршрут не заработает. Ссылки с `referenceGrant: false` не включаются
в разрешение. Если создание разрешения отключено для всех ссылок на этот
namespace, `ReferenceGrant` для него не создаётся. `ReferenceGrant` не даёт
доступа на сетевом уровне и не заменяет правила Istio. Их создаёт секция
`policies` в том же namespace, см. ниже.

Если включена только одна точка входа, можно не заполнять
`parentRefs[].gateway` и `hostnames`. Имя точки входа подставится
автоматически. Домены будут взяты из слушателя, на который ссылается маршрут.

## Секция `policies`

Один переключатель `enabled` создаёт `NetworkPolicy` и `AuthorizationPolicy`
вместе. По умолчанию он выключен. Правила вводить не нужно: чарт выводит
их из маршрутов. Прежние секции `networkPolicy` с `egress`
и `authorizationPolicy` останавливают рендер с подсказкой.

| Поле | Нужно указать | Что это |
|---|---|---|
| `enabled` | нет, по умолчанию `false` | Создание политик |
| `trustDomain` | нет, по умолчанию `cluster.local` | Домен доверия сетки, задаёт платформа |

Для подов каждой включённой точки входа в namespace релиза создаются:

- `NetworkPolicy` `{instance}-{cluster}-np-{project}-{gateway}`. Входящий
  трафик разрешён отовсюду на порты 80 и 443 и на служебные порты Istio
  15020, 15021 и 15090. Исходящий разрешён к istiod в `istio-system`
  на порт 15012, к CoreDNS в `kube-system` на порт 1053 по TCP и UDP
  и в каждый namespace, куда ведут `backendRefs` маршрутов этой точки
  входа: на порты сервисов и на порт 15008. По 15008 в ambient приходит
  трафик к поду в сетке, порт сервиса нужен поду вне сетки.
- `AuthorizationPolicy` `{instance}-{cluster}-ap-{project}-{gateway}`.
  Разрешает трафик с любого адреса.

Для каждого другого namespace, куда ведут `backendRefs`, рядом
с `ReferenceGrant` создаются ещё две политики с тем же именем, что
у разрешения, но со своим `kindShort`:

- `NetworkPolicy` `{instance}-{cluster}-np-{gateway}-{project}-routes`.
  Разрешает всем подам namespace вход от подов этой точки входа на те же
  порты.
- `AuthorizationPolicy` `{instance}-{cluster}-ap-{gateway}-{project}-routes`.
  Разрешает трафик от ServiceAccount точки входа
  (`{trustDomain}/ns/{namespace релиза}/sa/{имя Gateway}-istio`, его создаёт
  Istio) на порты сервисов. Селектора подов у политики нет: чарт знает имена
  сервисов, а не метки их подов, поэтому она покрывает весь namespace
  и сужает трафик источником и портами.

Istio после первой разрешающей политики запрещает всё, что не разрешено
явно. Если в namespace сервиса других политик нет, остальной трафик
к его подам в сетке остановится. Учитывайте это, включая политики
для сервисов в чужом namespace.

Ссылка с `referenceGrant: false` выключает политики в том namespace так же,
как и само разрешение: их создают владельцы namespace. Выход точки входа
в тот namespace при этом остаётся.

Порт в политиках берётся из `backendRefs[].port`, то есть из порта сервиса.
Он должен совпадать с портом контейнера, иначе трафик к поду вне сетки
не пройдёт. Протокол берётся из типа маршрута: UDP для `UDPRoute`, TCP
для остальных.

## Секция `oidcAuth`

Включите секцию, если приложению нужен вход по единой учётной записи.
По умолчанию она выключена.

При включении создаются маршрут для `/oauth2`, `ReferenceGrant`,
две `AuthorizationPolicy` и `RequestAuthentication`. Одна политика
отвечает за внешнюю авторизацию, другая проверяет группы пользователя.

Заполните обязательные поля: `application`, `gateway`,
`groupsPolicy.allowedGroups`, `keycloak.issuer` и `keycloak.jwksUri`.

## Когда рендер останавливается

Чарт проверяет значения перед созданием ресурсов. Если конфигурация
неполная или содержит ошибку, рендер останавливается и указывает поле,
которое нужно исправить.

Рендер остановится в следующих случаях:

- Не заданы `identity.instance` или `identity.cluster` либо в них указаны
  недопустимые символы.
- Значение `identity.project` длиннее 9 символов или содержит недопустимые
  символы.
- Имя точки входа или слушателя короче 2 или длиннее 9 символов.
  Имя маршрута или сертификата из хранилища короче 2 или длиннее 6 символов.
- У слушателя не указан порт или протокол.
- У слушателя с протоколом `HTTPS` или `TLS` не указан `hostname`.
- Домен слушателя с `tlsMode: Terminate` не покрыт ни одной записью
  `tls.certificates` и не разрешён платформенному издателю.
- Домен слушателя с `tlsMode: Terminate` не покрыт ни одной записью
  `tls.certificates`, автоматический выпуск выключен и `certificateRefs`
  не заданы.
- В записи `tls.certificates` не указан `domain`. Для сертификата из
  хранилища не указан `name` или `path` либо не задано хранилище
  ни в `store` записи, ни в `tls.store`. Для готового секрета
  не указан `secretName`.
- У маршрута не заданы `parentRefs` или `rules`.
- Повторяются имена двух включённых точек входа, двух слушателей одной
  точки входа, двух маршрутов одного типа на одной точке входа
  или двух записей в `tls.certificates`.
- В `kind` указан тип маршрута, которого нет в списке поддерживаемых.
- Для маршрута `TLS`, `TCP` или `UDP` заданы `matches` или `filters`.
- Для маршрута, кроме `HTTPRoute`, заданы `timeouts`, либо в `timeouts`
  указано поле, кроме `request` и `backendRequest`, либо длительность
  не в формате Gateway API.
- В `backendRefs` не указано имя или порт сервиса.
- В правиле два фильтра `RequestRedirect`, либо `RequestRedirect` вместе
  с `URLRewrite`, либо `RequestRedirect` вместе с `backendRefs`.
- В `sessionAffinity` не указан `cookieName`, либо `ttl` не число секунд
  с суффиксом `s`, либо в `h2UpgradePolicy` значение, кроме `DO_NOT_UPGRADE`
  и `UPGRADE`, либо два элемента `backendRefs[]` задают одному сервису
  разные cookie, `ttl` или `h2UpgradePolicy`, либо просят `DestinationRule`
  для сервисов с одним именем в разных namespace.
- В `proxy` точки входа `streamIdleTimeout` не число секунд с суффиксом `s`
  или `maxRequestHeadersKb` вне диапазона от 1 до 8192.
- В значениях есть секция `networkPolicy` или `authorizationPolicy`:
  с версии 10.0.0 их заменяет `policies.enabled`.

## Файлы чарта

| Файл                  | Для чего                                                                |
|-----------------------|--------------------------------------------------------------------------|
| `values.yaml`         | Значения по умолчанию. Секции пустые, ресурсы не создаются.               |
| `values.minimal.yaml` | Короткий рабочий пример с одной точкой входа, одним маршрутом и политиками. |
| `values.full.yaml`    | Полный справочник параметров с пояснениями.                              |
| `values.schema.json`  | Проверка значений при установке и форма заказа в портале.                |
| `view.schema.json`    | Настройки вида формы заказа и карточки сервиса в портале.                |
