# ingress-gateway

Чарт разворачивает вход в кластер на базе Istio и Kubernetes Gateway API. Вы
описываете в значениях точки входа и маршруты до сервисов, а чарт создаёт
`Gateway`, маршруты, сетевые политики и, если нужно, вход через OIDC.

## Что создаёт чарт

Значения разбиты на независимые секции, использовать можно любую или сразу
несколько.

| Секция                | Что создаётся                                                              | Когда брать                                       |
|-----------------------|----------------------------------------------------------------------------|---------------------------------------------------|
| `gateways[]`          | `Gateway` и инфраструктурный `ConfigMap` на каждый элемент                  | Нужна точка входа в кластер                       |
| `xroutes[]`           | `HTTPRoute`, `GRPCRoute`, `TLSRoute`, `TCPRoute` или `UDPRoute`             | Нужно довести трафик от точки входа до сервиса    |
| `tls`                 | `Certificate` (cert-manager) на каждую точку входа, чей домен вы не описали сами, и `ExternalSecret` на каждый описанный сертификат из хранилища | Точка входа расшифровывает TLS сама |
| `networkPolicy`       | `NetworkPolicy` для workload'а каждого Gateway                              | Нужно ограничить, куда ходит сам шлюз             |
| `authorizationPolicy` | `AuthorizationPolicy` (Istio) для workload'а каждого Gateway                | Нужны правила Istio на трафик к шлюзу             |
| `oidcAuth`            | `HTTPRoute`, `ReferenceGrant`, две `AuthorizationPolicy` и `RequestAuthentication` | Вход в приложение должен идти через Keycloak |

Секции связаны по именам: `xroutes[].parentRefs[].gateway` указывает на
`gateways[].name`, а `sectionName` - на `listeners[].name` этого Gateway.

## Куда ставится релиз

Все ресурсы создаются в namespace релиза. Исключение - `oidcAuth`: его ресурсы
раскладываются по namespace приложения, шлюза и oauth2-proxy, потому что вход
через OIDC связывает три стороны.

## Теги окружения и проекта

Секция `identity` задаётся один раз на релиз. Из неё собираются имена ресурсов
и labels, по которым ресурсы потом находятся в кластере.

| Поле                | Что это                                                                       |
|---------------------|--------------------------------------------------------------------------------|
| `identity.instance` | Тег инстанса окружения. Обязателен, значение из таблицы ниже                    |
| `identity.cluster`  | Тег кластера окружения. Обязателен, значение из таблицы ниже                    |
| `identity.project`  | Тег проекта. Обязателен, до 9 символов: строчные латинские буквы, цифры и дефис |

Дефис в теге проекта не может быть первым или последним символом.

Пара тегов окружения:

| Окружение      | `identity.cluster` | `identity.instance` |
|----------------|--------------------|---------------------|
| Infra-dev-ecpk | `inf`              | `in`                |
| dev-ecpk       | `dev`              | `id`                |
| techsec-dev    | `tco`              | `ed`                |
| dev-common     | `dev`              | `ed`                |
| test-common    | `tst`              | `ed`                |
| global         | `gl`               | `pr`                |
| observability  | `obs`              | `pr`                |
| techsec        | `tcc`              | `pr`                |
| int-common     | `cmi`              | `pr`                |
| ML             | `ml`               | `pr`                |
| ext-common     | `cme`              | `pr`                |

Оба поля описаны в схеме значений перечислением, поэтому в форме портала они
выбираются из списка. Берите значения строкой таблицы: схема проверяет каждое
поле по отдельности и не поймает пару из разных окружений.

## Имена ресурсов

Имя каждого ресурса собирается из пяти частей:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

- `instance`, `cluster`, `project` - теги из секции `identity`;
- `kindShort` подставляется по типу ресурса, см. таблицу ниже;
- `name` - имя элемента секции: строчные латинские буквы, цифры и дефис.
  У Gateway и точки входа от 2 до 9 символов, у маршрута и сертификата из
  хранилища от 2 до 6.

У маршрута и у сертификата между `kindShort` и проектом стоит имя гейтвея:

```
{instance}-{cluster}-{kindShort}-{gateway}-{project}-{name}
```

У маршрута гейтвей берётся из первого `parentRefs`, у сертификата - из той точки
входа, которая его использует. Поэтому одно имя можно использовать на разных
гейтвеях: `ed-dev-hr-edge-a-nbox-app` и `ed-dev-hr-edge-b-nbox-app` - разные
ресурсы, и так же разойдутся секреты двух заказов в одном неймспейсе. Внутри
одного гейтвея имя маршрута каждого типа остаётся уникальным, иначе рендер
останавливается.

Сертификат из хранилища, который нужен нескольким точкам входа одного гейтвея,
создаётся один раз. Тот же сертификат на другом гейтвее - это отдельный секрет,
читающий ту же запись хранилища.

Сертификат, который выпускается автоматически, называется по своей точке входа,
а не по записи: `{instance}-{cluster}-cert-{gateway}-{project}-{listener}`. Поэтому
имена точек входа одного гейтвея не могут повторяться, иначе рендер остановится.

| Тип ресурса           | `kindShort` | Тип ресурса | `kindShort` |
|-----------------------|-------------|-------------|-------------|
| `Gateway`             | `igw`       | `HTTPRoute` | `hr`        |
| `ConfigMap`           | `cm`        | `GRPCRoute` | `gr`        |
| `NetworkPolicy`       | `np`        | `TLSRoute`  | `tr`        |
| `AuthorizationPolicy` | `ap`        | `TCPRoute`  | `tcr`       |
| `Secret` (TLS)        | `secret`    | `UDPRoute`  | `ur`        |
| `ExternalSecret`      | `es`        | `Certificate` | `cert`    |

ConfigMap носит то же имя, что и его Gateway, только с `cm` вместо `igw`.
Итоговое имя обрезается до 63 символов. Примеры: `ed-dev-igw-nbox-main`,
`ed-dev-hr-nbox-app`.

Ресурсы OIDC этой схеме не следуют: их имена задаются в секции `oidcAuth`
вручную.

## Labels на ресурсах

На каждый ресурс чарта проставляется:

| Label                          | Значение                                                |
|--------------------------------|---------------------------------------------------------|
| `app`                          | `ingress-gateway` - имя чарта, не зависит от имени релиза |
| `app.kubernetes.io/name`       | Тег проекта из `identity.project`                        |
| `app.kubernetes.io/instance`   | Имя релиза                                               |
| `app.kubernetes.io/managed-by` | `Helm`                                                   |
| `app.kubernetes.io/version`    | Версия приложения из чарта                               |
| `helm.sh/chart`                | Имя и версия чарта                                       |
| `ecpk/instance`                | `identity.instance`, если тег задан                      |
| `ecpk/cluster`                 | `identity.cluster`, если тег задан                       |
| `ecpk/project`                 | `identity.project`, если тег задан                       |

Значения `ecpk/*` приводятся к нижнему регистру, то есть совпадают с тем, что
попало в имя ресурса. По ним отбираются все ресурсы окружения или проекта.

Свои labels и annotations добавляются через `generic.labels` и
`generic.annotations`. Задаются только на весь релиз сразу, отдельно по ресурсам
их не задать.

## Секция `gateways[]`

Один элемент - одна точка входа: создаются `Gateway` и инфраструктурный
`ConfigMap` с одинаковым именем и разным `kindShort`.

| Поле          | Нужно указать            | Что это                                                                     |
|---------------|--------------------------|------------------------------------------------------------------------------|
| `name`        | да                       | Имя, от 2 до 9 символов. На него ссылаются маршруты                          |
| `enabled`     | нет, по умолчанию `true` | При `false` ни Gateway, ни ConfigMap не создаются                            |
| `ipAddress`   | нет                      | Постоянный адрес балансировщика, уходит в аннотацию MetalLB                  |
| `hpa`         | нет                      | Автомасштабирование: `enabled`, `minReplicas`, `maxReplicas`, `averageUtilization` |
| `resources`   | нет                      | Ресурсы контейнера `istio-proxy`                                             |
| `listeners[]` | да                       | Список listener'ов, см. ниже                                                 |

Listener описывается полями:

- `name` - имя, на него ссылается маршрут через `sectionName`. Длина не ограничена.
- `port` и `protocol` - обязательны. Протокол: `HTTP`, `HTTPS`, `TCP`, `UDP` или `TLS`.
- `hostname` - обязателен для `HTTPS` и `TLS`. У `TCP` и `UDP` домена нет: в
  форме заказа поле для них скрыто, а из values значение в Gateway не попадает.
- `tlsMode` - `Terminate` (по умолчанию для `HTTPS`) или `Passthrough` (для `TLS`).
- `certificateRefs` - для `Terminate`, если сертификат уже лежит в кластере под
  своим именем. Иначе он берётся из секции `tls`, см. ниже.
- `allowedRoutes` - какие маршруты listener принимает.

## Секция `tls` - сертификаты

Listener с `tlsMode: Terminate` расшифровывает трафик сам, поэтому ему нужен
сертификат на свой домен. Взять его можно тремя способами, и по умолчанию
работает первый.

### Выпустить автоматически

Ничего заполнять не нужно: домен вы уже ввели у точки входа. Чарт создаёт
`Certificate`, cert-manager подписывает его у платформенного издателя и кладёт
в namespace секрет `kubernetes.io/tls`.

Один `Certificate` создаётся на одну точку входа. Две точки входа на одном
домене получат по своему сертификату: так имя каждого секрета выводится из
своей точки входа и не зависит от порядка списка.

Платформенный издатель подписывает не любой домен. Если ваш домен ему не
разрешён, рендер остановится и назовёт домен, а вы опишете сертификат одним из
способов ниже. Настройки издателя лежат в `tls.issuer` и в форме заказа не
показываются.

### Взять из хранилища

Сертификат и ключ лежат в Vault. Чарт создаёт `ExternalSecret`, External
Secrets Operator читает по нему запись и держит в namespace секрет
`kubernetes.io/tls`. В значениях заказа едет только путь: ни ключ, ни сам
сертификат в репозиторий не попадают.

| Поле          | Нужно указать | Что это                                                       |
|---------------|---------------|----------------------------------------------------------------|
| `source`      | нет           | `vault`, оно же значение по умолчанию                          |
| `name`        | да            | Имя от 2 до 6 символов, попадает в имя секрета                 |
| `domain`      | да            | Домен, который покрывает сертификат                            |
| `path`        | да            | Запись в Vault, в которой лежат сертификат и ключ              |
| `store`       | нет           | Имя `SecretStore`, если это не `tls.store` по умолчанию        |
| `crtProperty` | нет           | Ключ сертификата внутри записи, по умолчанию `tls.crt`         |
| `keyProperty` | нет           | Ключ приватного ключа внутри записи, по умолчанию `tls.key`    |

### Взять готовый секрет

Сертификат уже лежит в вашем namespace секретом `kubernetes.io/tls`, и принесли
его не этим чартом. Чарт ничего не создаёт и только ссылается на секрет.

| Поле         | Нужно указать | Что это                                    |
|--------------|---------------|--------------------------------------------|
| `source`     | да            | `existing`                                 |
| `domain`     | да            | Домен, который покрывает сертификат        |
| `secretName` | да            | Имя секрета в вашем namespace              |

Короткого имени у такой записи нет: секрет уже назван.

Список один - `tls.certificates`, в нём лежат записи обоих последних видов.
Домены любого уровня и не только в `ecpk.test`.

### Из какого хранилища читается сертификат

Сертификаты читаются через `SecretStore`: он живёт в том же namespace, что и
релиз, и ходит в Vault от вашей роли.

Хранилище записи - её `store`, а если он не задан - `tls.store`.

### Какой сертификат достанется точке входа

Сертификат для listener'а выбирается по его `hostname` среди
`tls.certificates`, первое совпадение выигрывает. Домен, который не покрыт ни
одной записью, выпускается автоматически.

Первое совпадение считается сверху вниз, поэтому запись со звёздочкой,
стоящая выше, перехватит домен у более точной записи ниже. Точную запись
ставьте перед общей.

Домен со звёздочкой покрывает один уровень, ровно как и сам сертификат:

| Домен записи      | Покрывает                              | Не покрывает                          |
|-------------------|----------------------------------------|---------------------------------------|
| `*.idp.ecpk.test` | `app.idp.ecpk.test`, `*.idp.ecpk.test` | `idp.ecpk.test`, `a.str.idp.ecpk.test` |
| `*.str.idp.ecpk.test` | `a.str.idp.ecpk.test`              | `b.a.str.idp.ecpk.test`               |
| `shop.example.ru` | `shop.example.ru`                      | `www.shop.example.ru`                 |

Поэтому поддомен четвёртого и пятого уровня описывается своей записью, даже
если он лежит внутри домена, уже описанного записью со звёздочкой.

Имена ресурсов у сертификата из хранилища собираются из `name` записи, а у
выпущенного автоматически - из имени точки входа:

| Ресурс           | Имя                                                         |
|------------------|--------------------------------------------------------------|
| `Secret`         | `{instance}-{cluster}-secret-{gateway}-{project}-{name}`      |
| `ExternalSecret` | `{instance}-{cluster}-es-{gateway}-{project}-{name}`          |
| `Certificate`    | `{instance}-{cluster}-cert-{gateway}-{project}-{listener}`    |
| `Secret` (автовыпуск) | `{instance}-{cluster}-secret-{gateway}-{project}-{listener}` |

Один сертификат из хранилища - один `ExternalSecret`, сколько бы listener'ов на
него ни ссылалось. Записи, которые не понадобились ни одному listener'у, не
создают ничего.

Если сертификат уже лежит в кластере под своим именем и приносит его не эта
секция, у listener'а задаются `certificateRefs`. Тогда чарт для него не создаёт
ни `ExternalSecret`, ни `Certificate`.

### Что происходит при удалении заказа

`ExternalSecret` уносит свой секрет с собой, а `Certificate` уезжает с релизом
и оставляет выпущенный секрет в namespace. Это не мешает: новый заказ с тем же
именем перезапишет его при первом же выпуске.

## Секция `xroutes[]`

| Поле           | Нужно указать                 | Что это                                                                 |
|----------------|-------------------------------|--------------------------------------------------------------------------|
| `name`         | да                            | Имя, от 2 до 6 символов                                                  |
| `enabled`      | нет, по умолчанию `true`      | При `false` маршрут не создаётся                                         |
| `kind`         | нет, по умолчанию `HTTPRoute` | `HTTPRoute`, `GRPCRoute`, `TLSRoute`, `TCPRoute` или `UDPRoute`          |
| `parentRefs[]` | да                            | `gateway` (имя из `gateways[]`) и `sectionName` (имя listener'а)         |
| `hostnames[]`  | для HTTP, GRPC и TLS          | Имена хостов, у TLS это SNI                                              |
| `rules[]`      | да                            | `matches` и `filters` только для HTTP и GRPC, `backendRefs` обязателен    |

В `backendRefs` обязательны `name` и `port`, а `namespace` и `weight` задаются
по желанию.

Если включённый Gateway один, часть полей можно не писать: `parentRefs[].gateway`
подставится сам, а `hostnames` возьмутся из listener'а, на который ссылается
маршрут.

## Секция `networkPolicy`

По умолчанию включена. На каждый включённый Gateway создаётся `NetworkPolicy`
для его workload'а. Входящий трафик разрешён на служебные порты Istio
(80, 443, 15020, 15021, 15090). Секцию `egress` задаёте вы, и при включённой
политике она обязательна.

## Секция `authorizationPolicy`

По умолчанию включена. На каждый включённый Gateway создаётся
`AuthorizationPolicy` Istio, по умолчанию разрешающая трафик с любого адреса.
Тонкая настройка правил в разработке.

## Секция `oidcAuth`

По умолчанию выключена. При включении создаются маршрут для `/oauth2`,
`ReferenceGrant`, две `AuthorizationPolicy` (внешняя авторизация и проверка
групп) и `RequestAuthentication`. Обязательны `application`, `gateway`,
`groupsPolicy.allowedGroups`, а также `keycloak.issuer` и `keycloak.jwksUri`.

## Когда рендер останавливается

Чарт не даёт выпустить незаконченную конфигурацию и называет поле, из-за
которого остановился:

- не заданы `identity.instance` или `identity.cluster` либо в них недопустимые
  символы;
- `identity.project` длиннее 9 символов или содержит недопустимые символы;
- имя Gateway или точки входа короче 2 или длиннее 9 символов, имя маршрута или
  сертификата из хранилища короче 2 или длиннее 6 символов;
- у listener'а не задан порт или протокол;
- у listener'а с протоколом `HTTPS` или `TLS` не задан hostname;
- у listener'а с `tlsMode: Terminate` домен не покрыт ни одной записью
  `tls.certificates` и не разрешён платформенному издателю;
- у listener'а с `tlsMode: Terminate` домен не покрыт ни одной записью
  `tls.certificates`, автовыпуск выключен и не заданы `certificateRefs`;
- у записи в `tls.certificates` не задан `domain`, у записи из хранилища не
  задан `name` или `path` либо негде взять хранилище (не задан ни `store`
  записи, ни `tls.store`), у записи с готовым секретом не задан `secretName`;
- у маршрута не заданы `parentRefs` или `rules`;
- два включённых гейтвея названы одинаково, две точки входа одного гейтвея
  названы одинаково, два маршрута одного типа на одном гейтвее названы
  одинаково или две записи в `tls.certificates` носят одно имя;
- `kind` маршрута не из поддерживаемого списка;
- для маршрута `TLS`, `TCP` или `UDP` заданы `matches` или `filters`;
- в `backendRefs` не задано имя или порт сервиса;
- сетевая политика включена, но `networkPolicy.egress` не задан.
