# egress-gateway

Чарт разворачивает выход из кластера наружу по ambient-схеме Istio: egress-шлюз -
это waypoint, а при необходимости к нему добавляется `VpcEgressGateway` kube-ovn.
Вы перечисляете внешние сервисы, к которым нужен доступ, а чарт создаёт шлюз и
все сопутствующие ресурсы. Ориентир схемы - официальная документация Istio по
ambient egress gateway.

## Что создаёт чарт

| Секция                | Что создаётся                    | Когда брать                                       |
|-----------------------|----------------------------------|---------------------------------------------------|
| `egressGateway`       | Один `Gateway` класса `istio-waypoint` и его `ConfigMap` | Нужен выход к внешним сервисам через Istio |
| `serviceEntries[]`    | `ServiceEntry`, привязанный к шлюзу лейблом | Опишите каждый внешний сервис, к которому ходите  |
| `networkPolicy`       | Две `NetworkPolicy` на поды шлюза | Шлюз должен ходить только по согласованным адресам |
| `authorizationPolicy` | `AuthorizationPolicy` (Istio)    | К шлюзу должны попадать только ваши сервисы       |
| `vpcEgressGateway[]`  | `VpcEgressGateway` (kube-ovn)    | Выход нужен на уровне VPC: внешние адреса и SNAT  |

На релиз создаётся один шлюз - waypoint с одним listener'ом `mesh` (порт 15008,
протокол HBONE). Маршруты задавать не нужно: `ServiceEntry` каждого внешнего
сервиса несёт лейбл `istio.io/use-waypoint` с именем шлюза, и ztunnel сам
туннелирует трафик к этому домену в waypoint по HBONE, а тот выпускает его
наружу. Политики и `VpcEgressGateway` нацеливаются на поды этого шлюза. Поэтому
все остальные секции работают только вместе с включённым `egressGateway`.

Namespace ваших сервисов чарт берёт из `serviceEntries[]` один раз и дальше
подставляет везде: в `NetworkPolicy` на входящий трафик, в `AuthorizationPolicy`
и в `allowedRoutes` listener'а шлюза. Дважды одно и то же вписывать не нужно.

Namespace отправителей должны быть в ambient-режиме
(`istio.io/dataplane-mode=ambient`): трафик до внешнего сервиса перехватывает
ztunnel, без него до waypoint ничего не дойдёт.

## Куда ставится релиз

Шлюз, его `ConfigMap`, обе политики и `VpcEgressGateway` создаются в namespace
релиза.

`ServiceEntry` уезжает в namespace вашего сервиса, если вы его назвали, и
остаётся рядом со шлюзом, если поле оставлено пустым. Когда namespace чужой,
`ServiceEntry` получает второй лейбл `istio.io/use-waypoint-namespace` с
namespace шлюза, а listener шлюза допускает namespace отправителя через
`allowedRoutes`: без этого привязка к waypoint из чужого namespace не действует.

## Теги окружения и проекта

Секция `identity` задаётся один раз на релиз. Из неё собираются имена ресурсов
и labels, по которым ресурсы потом находятся в кластере.

| Поле                | Что это                                                                       |
|---------------------|--------------------------------------------------------------------------------|
| `identity.instance` | Тег инстанса окружения. Обязателен, значение из таблицы ниже                    |
| `identity.cluster`  | Тег кластера окружения. Обязателен, значение из таблицы ниже                    |
| `identity.project`  | Тег проекта. Обязателен, до 9 символов: строчные латинские буквы, цифры и дефис |

Дефис в теге проекта не может быть первым или последним символом.

Пара тегов окружения:

| Окружение      | `identity.cluster` | `identity.instance` |
|----------------|--------------------|---------------------|
| Infra-dev-ecpk | `inf`              | `in`                |
| dev-ecpk       | `dev`              | `id`                |
| techsec-dev    | `tco`              | `ed`                |
| dev-common     | `dev`              | `ed`                |
| test-common    | `tst`              | `ed`                |
| global         | `gl`               | `pr`                |
| observability  | `obs`              | `pr`                |
| techsec        | `tcc`              | `pr`                |
| int-common     | `cmi`              | `pr`                |
| ML             | `ml`               | `pr`                |
| ext-common     | `cme`              | `pr`                |

Оба поля описаны в схеме значений перечислением, поэтому в форме портала они
выбираются из списка. Берите значения строкой таблицы: схема проверяет каждое
поле по отдельности и не поймает пару из разных окружений.

## Имена ресурсов

Имя каждого ресурса собирается из пяти частей:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

- `instance`, `cluster`, `project` - теги из секции `identity`;
- `kindShort` - `egw` для ресурсов Istio (`Gateway`, `ConfigMap`,
  `ServiceEntry`), `np` для `NetworkPolicy`, `ap` для `AuthorizationPolicy` и
  `veg` для `VpcEgressGateway`;
- `name` - имя элемента: от 2 до 6 символов, строчные латинские буквы, цифры и
  дефис.

`ConfigMap` и `AuthorizationPolicy` носят то же имя, что и их `Gateway`.
Итоговое имя обрезается до 63 символов. Пример: `ed-dev-egw-nbox-eg`.
`Deployment` и `Service` шлюза создаёт Istio и называет их именем `Gateway`.

У `NetworkPolicy` перед проектом стоит имя шлюза, потому что на один шлюз их
пара:

```
{instance}-{cluster}-np-{gatewayName}-{project}-{out|in}
```

Примеры: `ed-dev-np-eg-nbox-out`, `ed-dev-np-eg-nbox-in`.

## Labels на ресурсах

На каждый ресурс чарта проставляется:

| Label                          | Значение                                               |
|--------------------------------|--------------------------------------------------------|
| `app`                          | `egress-gateway` - имя чарта, не зависит от имени релиза |
| `app.kubernetes.io/name`       | Тег проекта из `identity.project`                       |
| `app.kubernetes.io/instance`   | Имя релиза                                              |
| `app.kubernetes.io/managed-by` | `Helm`                                                  |
| `app.kubernetes.io/version`    | Версия приложения из чарта                              |
| `helm.sh/chart`                | Имя и версия чарта                                      |
| `ecpk/instance`                | `identity.instance`, если тег задан                     |
| `ecpk/cluster`                 | `identity.cluster`, если тег задан                      |
| `ecpk/project`                 | `identity.project`, если тег задан                      |

Значения `ecpk/*` приводятся к нижнему регистру, то есть совпадают с тем, что
попало в имя ресурса. По ним отбираются все ресурсы окружения или проекта.

Свои labels и annotations добавляются через `generic.labels` и
`generic.annotations`. Задаются только на весь релиз сразу, отдельно по ресурсам
их не задать.

## Секция `egressGateway`

Один шлюз на релиз: создаются `Gateway` и `ConfigMap` с одинаковым именем.

| Поле        | Нужно указать            | Что это                                        |
|-------------|--------------------------|-------------------------------------------------|
| `name`      | да                       | Имя шлюза, от 2 до 6 символов                   |
| `enabled`   | нет, по умолчанию `true` | При `false` из этой секции ничего не создаётся  |
| `hpa`       | нет                      | Автомасштабирование шлюза, см. ниже             |
| `resources` | нет                      | Ресурсы контейнера шлюза, есть значение по умолчанию |

Шлюз - это waypoint: `Gateway` класса `istio-waypoint` с лейблом
`istio.io/waypoint-for: service` и одним listener'ом `mesh` на порту 15008
(протокол HBONE). Настраивать в нём нечего: точки выхода не нужны, внешние
сервисы привязываются к шлюзу лейблом на своём `ServiceEntry`.

Автомасштабирование:

| Поле                     | Нужно указать             | Что это                                    |
|--------------------------|---------------------------|---------------------------------------------|
| `hpa.enabled`            | нет, по умолчанию `false` | Добавлять экземпляры под нагрузкой          |
| `hpa.minReplicas`        | нет, по умолчанию `2`     | Столько экземпляров работает всегда         |
| `hpa.maxReplicas`        | нет, по умолчанию `5`     | Выше этого числа шлюз не поднимется         |
| `hpa.averageUtilization` | нет, по умолчанию `80`    | Загрузка CPU в процентах, выше которой добавляется экземпляр |

## Секция `serviceEntries[]`

Один элемент - один внешний сервис, к которому ходят ваши приложения.

| Поле        | Нужно указать            | Что это                                                          |
|-------------|--------------------------|-------------------------------------------------------------------|
| `name`      | да                       | Имя, от 2 до 6 символов. Попадает в имя `ServiceEntry`            |
| `hostname`  | да                       | Домен внешнего сервиса                                            |
| `namespace` | нет                      | Namespace отправителя. Пусто - тот же namespace, что у шлюза      |
| `enabled`   | нет, по умолчанию `true` | При `false` `ServiceEntry` не создаётся                           |

На каждую запись чарт создаёт один `ServiceEntry` рядом с отправителем и вешает
на него лейбл `istio.io/use-waypoint` с именем шлюза. Этого достаточно: ztunnel
перехватывает трафик приложений к этому домену и туннелирует его в waypoint по
HBONE, тот выпускает его наружу. Порт всегда 443.

Остальное чарт заполняет сам: сервис считается внешним по отношению к mesh, его
адрес ищется по домену, порт описывается как TLS. `ServiceEntry` виден в своём
namespace и, когда отправитель лежит отдельно, ещё и в namespace шлюза; при
чужом namespace он получает и лейбл `istio.io/use-waypoint-namespace`.

## Секция `networkPolicy`

Включается одним флагом и создаёт сразу две `NetworkPolicy` на поды шлюза.

| Поле          | Нужно указать             | Что это                                                     |
|---------------|---------------------------|--------------------------------------------------------------|
| `enabled`     | нет, по умолчанию `false` | При `true` создаются обе политики                            |
| `endpoints[]` | да, когда `enabled: true` | Адреса и порты, к которым шлюзу разрешено ходить             |

Политика `...-out` разрешает шлюзу исходящий трафик: до istiod
(namespace `istio-system`, порт 15012), до CoreDNS (namespace `kube-system`,
порт 1053 по TCP и UDP) и до каждого адреса из `endpoints[]`. Первые два адреса
зашиты в чарте, без них шлюз не работает.

Политика `...-in` разрешает входящий трафик на порт 15008 (HBONE, на нём
waypoint принимает туннель от ztunnel) из namespace ваших сервисов и из
namespace релиза. Список namespace чарт берёт из `serviceEntries[]`.

| Поле                    | Нужно указать | Что это                                             |
|-------------------------|---------------|------------------------------------------------------|
| `endpoints[].address`   | да            | IP внешней точки или подсеть в формате CIDR          |
| `endpoints[].port`      | да            | Порт, на который шлюз ходит по этому адресу          |

Одиночный IP чарт сам превращает в подсеть на один адрес.

## Секция `authorizationPolicy`

| Поле      | Нужно указать             | Что это                              |
|-----------|---------------------------|---------------------------------------|
| `enabled` | нет, по умолчанию `false` | При `true` создаётся правило доступа  |

Создаётся одно правило `ALLOW`, привязанное к шлюзу через `targetRefs`. Оно
пускает к шлюзу трафик из namespace ваших сервисов и из namespace релиза - тех
же, что и у `networkPolicy`. Больше в секции задавать нечего: источники чарт
выводит из `serviceEntries[]`.

## Секция `vpcEgressGateway[]`

| Поле          | Нужно указать            | Что это                                              |
|---------------|--------------------------|-------------------------------------------------------|
| `name`        | да                       | Имя, от 2 до 6 символов                               |
| `enabled`     | нет, по умолчанию `true` | При `false` ресурс не создаётся                       |
| `externalIPs` | да                       | Внешние адреса. Сколько адресов, столько и реплик     |

Остальное чарт заполняет сам: namespace релиза, число реплик по количеству
адресов, селекторы, указывающие на поды созданного шлюза, и правило SNAT на
подсеть, одноимённую namespace релиза. Параметры VPC (сама VPC, внешняя подсеть
`egress-vip`, политика трафика) зашиты в шаблоне и через значения не
настраиваются.

Выходы размещаются на мастер-узлах кластера. Ingress-шлюз сервиса работает на
воркерах, и делить с ним узел выходы не должны.

## Когда рендер останавливается

- не заданы `identity.instance` или `identity.cluster` либо в них недопустимые
  символы;
- `identity.project` длиннее 9 символов или содержит недопустимые символы;
- имя шлюза, внешнего сервиса или `VpcEgressGateway` короче 2 или длиннее 6
  символов;
- у шлюза не задано имя;
- список внешних сервисов пуст: waypoint без привязанных `ServiceEntry` не несёт
  трафика;
- у внешнего сервиса не заданы имя или домен;
- namespace внешнего сервиса записан не в DNS-формате;
- один домен указан у двух внешних сервисов: они привязали бы его к шлюзу
  дважды;
- `networkPolicy.enabled: true`, а список `endpoints[]` пуст или у записи не
  задан адрес либо порт;
- у `VpcEgressGateway` не заданы имя или внешние адреса;
- заданы внешние сервисы, политики или `VpcEgressGateway`, а шлюз выключен либо
  у него нет имени;
- два внешних сервиса в одном namespace названы одинаково или два
  `VpcEgressGateway` названы одинаково: такие записи дали бы ресурсы с одним
  именем, из которых в кластере остался бы последний.

## Файлы чарта

| Файл                  | Для чего                                                             |
|-----------------------|-----------------------------------------------------------------------|
| `values.yaml`         | Значения по умолчанию: шлюза нет, ресурсы не создаются                 |
