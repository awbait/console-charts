# egress-gateway

Выход из кластера наружу с известного адреса: внешние системы видят ваш
трафик с согласованных IP. Заказ создаёт выход kube-ovn и, при необходимости,
egress-гейтвей в служебных неймспейсах по схеме ЕЦПК: два режима,
три неймспейса.

## Два режима

| | `mode: mesh` | `mode: direct` |
|---|---|---|
| Когда брать | Сервисы в сетке ambient | Сервисы без сетки |
| Что указываете | Внешние домены | Подсеть или метку подов |
| Через выход уходит | Трафик к указанным доменам | Весь внешний трафик |
| Кто ходит | Только ваши сервисы | Вся подсеть или поды с меткой |
| Куда можно ходить | Домены из списка, открытые межсетевым экраном | Всё, что разрешено межсетевым экраном |
| Гейтвей (waypoint) | В отдельном неймспейсе | Не создаётся |

В `mesh` остальной внешний трафик идёт как прежде. В `direct` перехвата
сеткой нет.

## Три неймспейса

| Неймспейс | Что внутри | Сетка | Кто создаёт |
|---|---|---|---|
| Ваших сервисов | Приложения | На ваш выбор | Заказ `namespace` заранее |
| Гейтвея | Egress-гейтвей | Всегда | Этот заказ в `mesh` |
| Выхода | Выход kube-ovn | Никогда | Этот заказ всегда |

Перехват ambient нарушает работу транзитного выхода, поэтому его неймспейс
исключён из сетки во всех кластерах. Служебные неймспейсы и гейтвей
создаются средствами `namespace` и `waypoint`, с теми же квотами, подсетями
и метками Pod Security, что и при отдельном заказе.

## Что создаёт заказ

| Секция | Что создаётся | Режим |
|---|---|---|
| `waypointNamespace` | Неймспейс с квотами, подсетью и гейтвеем | mesh |
| `vegNamespace` | Неймспейс с квотами и подсетью | оба |
| `vpcEgressGateway` | `VpcEgressGateway` kube-ovn | оба |
| `serviceEntries[]` | Записи `ServiceEntry` с привязкой к гейтвею | mesh |
| `networkPolicy` | Две политики гейтвея и одна ваших сервисов | mesh |
| `authorizationPolicy` | Правило `AuthorizationPolicy` гейтвея | mesh |

Гейтвей создаётся как `Gateway` класса `istio-waypoint` с `ConfigMap`.

Один заказ даёт один выход. Несколько внешних адресов дают столько же
экземпляров выхода. Для двух разных наборов адресов нужны два заказа.

## Где размещаются ресурсы

Ресурсы размещаются вне неймспейса релиза. Гейтвей и выход получают
собственные неймспейсы. В неймспейс ваших сервисов добавляются только
`ServiceEntry` и правило выхода к гейтвею. Сам неймспейс не меняется.

Имена служебных неймспейсов: `{project}-{cluster}-ns-{назначение}`.
Назначение гейтвея задаёт `global.namespacePurpose`, выхода -
`vegNamespace.namespace.name`. В форме уже указаны `egw-eg` и `veg-vip`.
С тегами `nbox`/`dev` получатся `nbox-dev-ns-egw-eg`
и `nbox-dev-ns-veg-vip`.

Для первого выхода оставьте назначения по умолчанию. Для следующего
выхода той же команды в том же кластере укажите другие, иначе заказы
попробуют создать одинаковые неймспейсы.

Обе служебные подсети неизолированные: гейтвею и выходу нужны внешние
адреса. Включение подсетей описано в секциях их настроек ниже.

## Теги окружения и проекта

Блок «Окружение и проект» (`global.identity`) задаёт общие теги для имён
всех ресурсов заказа. Портал подставляет окружение и команду, от имени
которой сделан заказ. Вручную блок заполняют только при прямой установке.

| Поле | Что это |
|---|---|
| `global.identity.instance` | Инстанс платформы |
| `global.identity.cluster` | Кластер |
| `global.identity.project` | Код проекта |

Все три поля обязательны. Тег проекта содержит до 9 символов:
строчные латинские буквы, цифры и дефис. Первый и последний символ -
буква или цифра.

| Окружение | `cluster` | `instance` |
|---|---|---|
| Infra-dev-ecpk | `inf` | `in` |
| dev-ecpk | `dev` | `id` |
| techsec-dev | `tco` | `ed` |
| dev-common | `dev` | `ed` |
| test-common | `tst` | `ed` |
| global | `gl` | `pr` |
| observability | `obs` | `pr` |
| techsec | `tcc` | `pr` |
| int-common | `cmi` | `pr` |
| ML | `ml` | `pr` |
| ext-common | `cme` | `pr` |

Инстанс и кластер выбираются из списков. Берите пару из одной строки:
схема проверяет поля отдельно и пропустит сочетание разных окружений.

## Имена ресурсов

Имена ресурсов собираются автоматически:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

Теги берутся из `global.identity`. Код типа: `egw` для `ServiceEntry`,
`np` для `NetworkPolicy`, `ap` для `AuthorizationPolicy`,
`veg` для `VpcEgressGateway`.

Поле `name` содержит от 2 до 9 символов: строчные латинские буквы,
цифры и дефис. Готовое имя обрезается до 63 символов,
например `ed-dev-veg-nbox-vip`.

У гейтвея код `wp`, а имя берётся из
`waypointNamespace.waypoint.waypoints[].name` и содержит от 2 до 6 символов.
Пример: `ed-dev-wp-nbox-eg`. Его `ConfigMap` получает то же имя,
`AuthorizationPolicy` - такое же с кодом `ap`. Istio создаёт `Deployment`
и `Service` с именем `Gateway`.

У трёх `NetworkPolicy` перед проектом стоит имя гейтвея:

```
{instance}-{cluster}-np-{gatewayName}-{project}-{out|in|senders}
```

Примеры: `ed-dev-np-eg-nbox-out`, `ed-dev-np-eg-nbox-in`,
`ed-dev-np-eg-nbox-senders`.

Подсети именуются по правилу `namespace`, например
`nbox-dev-subnet-egw-eg` для неймспейса `nbox-dev-ns-egw-eg`.

## Метки на ресурсах

Ресурсы самого `egress-gateway` получают метки:

| Метка | Значение |
|---|---|
| `app` | `egress-gateway`, независимо от имени релиза |
| `app.kubernetes.io/name` | Тег проекта из `global.identity.project` |
| `app.kubernetes.io/instance` | Имя релиза |
| `app.kubernetes.io/managed-by` | `Helm` |
| `app.kubernetes.io/version` | Версия приложения из чарта |
| `helm.sh/chart` | Имя и версия чарта |
| `ecpk/instance` | `global.identity.instance` |
| `ecpk/cluster` | `global.identity.cluster` |
| `ecpk/project` | `global.identity.project` |

Ресурсы `namespace` и `waypoint` имеют свои метки `app: namespace`
и `app: waypoint`. Общие теги `ecpk/*` позволяют найти весь заказ.

Свои метки и аннотации задавайте в `generic.labels` и
`generic.annotations`. Для ресурсов `namespace` и `waypoint` используйте
отдельные блоки `generic` внутри `waypointNamespace` и `vegNamespace`.

## Секция `mode`

Поле «Режим выхода» определяет способ выхода.

| Значение | Что это |
|---|---|
| `mesh` | Сервисы в сетке, по умолчанию |
| `direct` | Сервисы без сетки |

## Секция `senders`

Блок «Ваши сервисы» задаёт один существующий неймспейс на заказ.

| Поле | Нужно указать | Что это |
|---|---|---|
| `namespace` | да | Неймспейс сервисов |
| `subnet` | для всей подсети в `direct` | Подсеть сервисов |

Укажите имя подсети: `{проект}-{кластер}-subnet-{назначение}`,
например `nbox-dev-subnet-app`. Оно есть в карточке неймспейса
и в заказе на него.

## Секция `serviceEntries[]`

В блоке «Внешние сервисы» добавьте по записи на сервис для режима `mesh`.

| Поле | Нужно указать | Что это |
|---|---|---|
| `name` | да | Имя сервиса в имени `ServiceEntry` |
| `hostname` | да | Домен сервиса |
| `enabled` | нет, по умолчанию `true` | Создание записи |

При `enabled: false` запись не создаётся. Каждая созданная запись получает
метки `istio.io/use-waypoint` с именем гейтвея
и `istio.io/use-waypoint-namespace` с его неймспейсом.

По этим меткам сетка перехватывает трафик к домену и направляет его
туннелем HBONE в гейтвей, затем через выход наружу. Порт всегда 443,
протокол TLS. Адрес определяется по домену, сервис считается внешним
для сетки. Запись видна только вашим сервисам и неймспейсу гейтвея.
Эти настройки заполняются автоматически.

## Секция `vpcEgressGateway`

Блок «Выход наружу» задаёт адреса и выбор подов.

| Поле | Нужно указать | Что это |
|---|---|---|
| `name` | да | Имя выхода |
| `externalIPs` | да | Внешние IP-адреса |
| `scope` | нет, по умолчанию `namespace` | Источники трафика |
| `label` | нет, по умолчанию `ecpk/egress` | Ключ метки |
| `nodeSelector` | нет | Выбор узлов |
| `tolerations` | нет | Допуски размещения |

В `mesh` выход выбирает поды гейтвея. Поля `scope` и `label` действуют
только в `direct`:

- `scope: namespace` направляет через выход всю подсеть `senders.subnet`.
- `scope: label` выбирает поды ваших сервисов по ключу из `label`.
  Значение метки должно совпадать с именем выхода в кластере,
  например `ecpk/egress: ed-dev-veg-nbox-vip`.

Правила кластера разрешают такую метку только там, где заказан выход,
и запрещают сочетать её с сеткой.

VPC и внешняя подсеть `egress-vip` фиксированы и через значения
не настраиваются. Размещение подов задаёт `gatewayScheduling`.

## Секция `gatewayScheduling`

| Поле | Нужно указать | Что это |
|---|---|---|
| `nodeSelector` | нет | Выбор узлов |
| `tolerations` | нет | Допуски размещения |

Блок «Размещение выхода» задаёт общие правила для подов выхода.
В чарте оба поля пусты, узлы выбирает планировщик кластера.
Платформа может задать правила в значениях своей установки:
выделить группу узлов или исключить часть узлов.

`nodeSelector` использует формат kube-ovn: список условий
с `matchLabels`, `matchExpressions` и `matchFields`. Требования внутри
условия объединяются по «и», условия между собой по «или».

`tolerations` использует формат спецификации пода Kubernetes и разрешает
размещение на узлах с соответствующими ограничениями. Поля `affinity`
у `VpcEgressGateway` нет. Реплики по разным узлам распределяет kube-ovn.

Одноимённое поле в `vpcEgressGateway` целиком заменяет правило платформы
без слияния. Пустой список отключает это правило для данного выхода.
Все поля размещения скрыты в форме и задаются только в значениях.
Дополнительная настройка и повторный заказ существующих выходов не нужны.

## Секция `networkPolicy`

Блок «Сетевые правила» действует в режиме `mesh`.

| Поле | Нужно указать | Что это |
|---|---|---|
| `enabled` | нет, по умолчанию `false` | Ограничение трафика |
| `endpoints[]` | при `enabled: true` | Адреса и порты |
| `senders` | нет, по умолчанию `true` | Выход к гейтвею |

При включении создаются политики `NetworkPolicy`:

- `...-out` разрешает гейтвею выход к адресам из `endpoints[]`,
  к istiod в `istio-system` на порт 15012 и к CoreDNS в `kube-system`
  на порт 1053 по TCP и UDP. Доступ к istiod и CoreDNS фиксирован:
  без него гейтвей не работает.
- `...-in` разрешает вход из неймспейса ваших сервисов на порт 15008
  гейтвея, где он принимает туннели HBONE от сетки.
- `...-senders` разрешает всем подам ваших сервисов выход в неймспейс
  гейтвея на порт 15008.

Неймспейс в сетке использует правила платформы по умолчанию.
Без `...-senders` сетка не откроет туннель к гейтвею.
Укажите `senders: false`, только если этих правил в неймспейсе нет:
тогда добавление политики, наоборот, изолировало бы поды.

| Поле | Нужно указать | Что это |
|---|---|---|
| `endpoints[].address` | да | Адрес назначения: IP или подсеть CIDR |
| `endpoints[].port` | да | Порт назначения |

Одиночный IP автоматически превращается в подсеть на один адрес.

## Секция `authorizationPolicy`

Блок «Доступ к гейтвею» действует в режиме `mesh`.

| Поле | Нужно указать | Что это |
|---|---|---|
| `enabled` | нет, по умолчанию `false` | Ограничение доступа |

При включении создаётся одно правило `ALLOW` в неймспейсе гейтвея
с привязкой через `targetRefs`. Оно разрешает трафик только из неймспейса
ваших сервисов. Других настроек нет.

## Секции `waypointNamespace` и `vegNamespace`

Блоки «Неймспейс гейтвея» и «Неймспейс выхода» содержат настройки
служебных неймспейсов. Роль `egress`, квоты и уровень Pod Security
уже заданы: `baseline` для гейтвея, `privileged` для выхода.

| Поле | Нужно указать | Что это |
|---|---|---|
| `waypointNamespace.enabled` | `false` в `direct` | Создание неймспейса |
| `waypointNamespace.waypoint.waypoints` | в `mesh` | Один гейтвей |
| `*.subnet.enable`, `*.subnet.subnets[].cidrBlock` | после брони | Подсеть |

После резервирования диапазона укажите его в `cidrBlock` соответствующей
секции и включите `subnet.enable: true`.

В `waypointNamespace.waypoint.waypoints` опишите гейтвей:

| Поле | Нужно указать | Что это |
|---|---|---|
| `name` | да | Имя гейтвея |
| `allowedNamespaces` | да | Неймспейс ваших сервисов |
| `hpa` | нет | Автомасштабирование |
| `resources` | нет | Ресурсы контейнера гейтвея |

Без `allowedNamespaces` привязка `ServiceEntry` к гейтвею не действует.
В `hpa` доступны `enabled`, `minReplicas`, `maxReplicas`
и `averageUtilization`.

Описывайте элемент списка целиком: он не сливается со значениями
по умолчанию. Остальные поля описаны в чартах `namespace` и `waypoint`.

## Когда рендер останавливается

- Не задан `global.identity` или задан `identity` в корне.
- Теги содержат недопустимые символы или `project` длиннее 9 символов.
- Значение `mode` отличается от `mesh` и `direct`.
- Не задан `senders.namespace` или он совпадает с неймспейсом гейтвея
  либо выхода.
- У выхода не задано имя или пуст список внешних адресов.
- Не задано `vegNamespace.namespace.name` или оно совпадает
  с `global.namespacePurpose`.
- Роль неймспейса выхода отличается от `egress` или не задано
  `serviceMesh.never: true`.
- В режиме `mesh` не задано `global.namespacePurpose`.
- В режиме `mesh` выключен `waypointNamespace`, его сетка или вейпоинт.
- В режиме `mesh` задано `waypointNamespace.namespace.name`.
- В режиме `mesh` список вейпоинтов содержит не ровно один элемент.
- В режиме `mesh` неймспейс ваших сервисов отсутствует
  в `allowedNamespaces` гейтвея.
- В режиме `mesh` пуст список внешних сервисов.
- В режиме `mesh` у внешнего сервиса не задано имя или домен.
- В режиме `mesh` внешние сервисы повторяют имя или домен друг друга.
- В режиме `direct` включён `waypointNamespace`.
- В режиме `direct` заданы внешние сервисы или включены сетевые правила
  либо правило доступа.
- В режиме `direct` выбрана вся подсеть, но не задана `senders.subnet`.
- В режиме `direct` значение `scope` отличается от `namespace` и `label`.
- В режиме `direct` поле `label` не соответствует формату ключа метки.
- При `networkPolicy.enabled: true` пуст список `endpoints[]`
  или у записи не задан адрес либо порт.

Чарты `namespace` и `waypoint` также проверяют маску подсети,
формат CIDR и квоты.

## Файлы чарта

| Файл | Для чего |
|---|---|
| `values.yaml` | Настройки по умолчанию |
| `values.minimal.yaml` | Пример `mesh` с сервисом, политиками и выходом |
| `values.direct.yaml` | Пример `direct` для всей подсети сервисов |
| `values.full.yaml` | Все параметры с пояснениями |
| `values.schema.json` | Проверка при установке и форма заказа |
| `view.schema.json` | Вид формы заказа в портале |

В `values.yaml` зафиксированы настройки служебных неймспейсов.
Сервисы-отправители и внешние адреса в нём не заданы.
