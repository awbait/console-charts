# egress-gateway

Чарт разворачивает выход из кластера наружу с известного адреса. Внешняя
система видит ваш трафик с согласованных IP, а внутри кластера чарт создаёт всё,
что для этого нужно: до двух служебных неймспейсов, egress-гейтвей и выход
kube-ovn. Схема принята архитектурой ЕЦПК: два режима, три неймспейса.

## Два режима

| | `mode: mesh` | `mode: direct` |
|---|---|---|
| Когда брать | Ваши сервисы в сервисной сетке (ambient) | Ваши сервисы без сетки |
| Что указываете | Внешние домены, к которым ходите | Подсеть сервисов или метку на подах |
| Через выход уходит | Только перечисленные домены | Весь внешний трафик подсети (или подов с меткой) |
| Кто ходит | Только namespace ваших сервисов: правило доступа на гейтвее | Вся подсеть или помеченные поды |
| Куда можно ходить | Перечисленные домены и внешний межсетевой экран | Только внешний межсетевой экран |
| Гейтвей (waypoint) | Создаётся в своём namespace | Не создаётся |

В режиме mesh трафик к перечисленным доменам ztunnel перехватывает у ваших
сервисов, туннелирует в egress-гейтвей, а тот выпускает его через выход. Всё
остальное, что ваши сервисы делают наружу, идёт как прежде. В режиме direct
перехвата нет: через выход уходит всё, что покидает подсеть.

## Три неймспейса

| Namespace | Что внутри | Сетка | Кто создаёт |
|---|---|---|---|
| Ваших сервисов | Ваши приложения | По вашему выбору | Отдельный заказ `namespace`, до этого заказа |
| Гейтвея | Только egress-гейтвей | Всегда | Этот заказ, только в режиме mesh |
| Выхода | Только выход kube-ovn | Никогда | Этот заказ, всегда |

Выход - транзитный узел, и перехват ambient его ломает, поэтому его namespace
держится вне сетки в любом кластере. Гейтвею, напротив, сетка нужна всегда.
Оба служебных namespace чарт создаёт сабчартом `namespace`, а гейтвей внутри
своего namespace рендерит сабчарт `waypoint`: чарт не дублирует их шаблоны и
получает те же квоты, подсети и метки Pod Security, что и обычный заказ.

## Что создаёт чарт

| Секция                | Что создаётся                    | Режим  |
|-----------------------|----------------------------------|--------|
| `waypointNamespace`   | `Namespace` гейтвея, его квоты и подсеть, `Gateway` класса `istio-waypoint` с `ConfigMap` | mesh |
| `vegNamespace`        | `Namespace` выхода, его квоты и подсеть | оба |
| `vpcEgressGateway`    | `VpcEgressGateway` (kube-ovn) в namespace выхода | оба |
| `serviceEntries[]`    | `ServiceEntry` в namespace ваших сервисов, привязанный к гейтвею | mesh |
| `networkPolicy`       | Две `NetworkPolicy` на гейтвей и одна в namespace ваших сервисов | mesh |
| `authorizationPolicy` | `AuthorizationPolicy` на гейтвей | mesh |

Один выход на заказ: несколько внешних адресов дают несколько экземпляров
одного выхода. Нужны два разных набора адресов - это два заказа.

## Куда ставится релиз

Ресурсы чарта не встают в namespace релиза. `Namespace` гейтвея и `Namespace`
выхода чарт создаёт сам, и всё, что относится к гейтвею и выходу, ложится в них.
В namespace ваших сервисов чарт кладёт только `ServiceEntry` и правило выхода
к гейтвею. Сам namespace ваших сервисов чарт не создаёт и не меняет.

Namespace, которые создаёт чарт, называются по правилу чарта `namespace`:
`{project}-{cluster}-ns-{назначение}`. Назначение namespace гейтвея задаётся в
`global.namespacePurpose`, назначение namespace выхода - в
`vegNamespace.namespace.name`. Со значениями по умолчанию (`egw-eg` и `veg-vip`)
и тегами `nbox`/`dev` получится `nbox-dev-ns-egw-eg` и `nbox-dev-ns-veg-vip`.

Подсети обоих namespace чарт заказывает не изолированными: гейтвей и выход ходят
на внешние адреса. Включаются они, когда диапазон зарезервирован:
`subnet.enable: true` и `cidrBlock` у соответствующего сабчарта.

## Теги окружения и проекта

Секция `global.identity` задаётся один раз на релиз. Из неё собираются имена
всех ресурсов, и она же уходит в оба сабчарта `namespace` и в `waypoint`,
поэтому лежит в `global`, а не в корне: только `global` Helm передаёт
сабчартам. Блок `identity` в корне чарт не принимает.

| Поле                       | Что это                                                                       |
|----------------------------|--------------------------------------------------------------------------------|
| `global.identity.instance` | Тег инстанса окружения. Обязателен, значение из таблицы ниже                    |
| `global.identity.cluster`  | Тег кластера окружения. Обязателен, значение из таблицы ниже                    |
| `global.identity.project`  | Тег проекта. Обязателен, до 9 символов: строчные латинские буквы, цифры и дефис |

Дефис в теге проекта не может быть первым или последним символом.

Секцию в форме заказа не заполняют: теги окружения портал подставляет сам, а в
тег проекта уезжает команда, от имени которой сделан заказ. Заполняют её,
только когда чарт ставят напрямую.

Пара тегов окружения:

| Окружение      | `cluster` | `instance` |
|----------------|-----------|------------|
| Infra-dev-ecpk | `inf`     | `in`       |
| dev-ecpk       | `dev`     | `id`       |
| techsec-dev    | `tco`     | `ed`       |
| dev-common     | `dev`     | `ed`       |
| test-common    | `tst`     | `ed`       |
| global         | `gl`      | `pr`       |
| observability  | `obs`     | `pr`       |
| techsec        | `tcc`     | `pr`       |
| int-common     | `cmi`     | `pr`       |
| ML             | `ml`      | `pr`       |
| ext-common     | `cme`     | `pr`       |

Оба поля описаны в схеме значений перечислением, поэтому в форме портала они
выбираются из списка. Берите значения строкой таблицы: схема проверяет каждое
поле по отдельности и не поймает пару из разных окружений.

## Имена ресурсов

Имя каждого ресурса самого чарта собирается из пяти частей:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

- `instance`, `cluster`, `project` - теги из `global.identity`;
- `kindShort` - `egw` для `ServiceEntry`, `np` для `NetworkPolicy`, `ap` для
  `AuthorizationPolicy` и `veg` для `VpcEgressGateway`;
- `name` - имя элемента: от 2 до 9 символов, строчные латинские буквы, цифры и
  дефис.

Итоговое имя обрезается до 63 символов. Пример: `ed-dev-veg-nbox-vip`.

Гейтвей называет сабчарт `waypoint` по своему правилу с `kindShort` `wp` и
именем из `waypointNamespace.waypoint.waypoints[].name` (от 2 до 6 символов):
`ed-dev-wp-nbox-eg`. `ConfigMap` гейтвея носит то же имя, как и
`AuthorizationPolicy` (с `kindShort` `ap`). `Deployment` и `Service` гейтвея
создаёт Istio и называет их именем `Gateway`.

У `NetworkPolicy` перед проектом стоит имя гейтвея, потому что на один гейтвей
их три:

```
{instance}-{cluster}-np-{gatewayName}-{project}-{out|in|senders}
```

Примеры: `ed-dev-np-eg-nbox-out`, `ed-dev-np-eg-nbox-in`,
`ed-dev-np-eg-nbox-senders`.

Namespace и их подсети называет сабчарт `namespace`: `nbox-dev-ns-egw-eg`,
`nbox-dev-subnet-egw-eg`.

## Labels на ресурсах

На каждый ресурс самого чарта проставляется:

| Label                          | Значение                                               |
|--------------------------------|--------------------------------------------------------|
| `app`                          | `egress-gateway` - имя чарта, не зависит от имени релиза |
| `app.kubernetes.io/name`       | Тег проекта из `global.identity.project`                |
| `app.kubernetes.io/instance`   | Имя релиза                                              |
| `app.kubernetes.io/managed-by` | `Helm`                                                  |
| `app.kubernetes.io/version`    | Версия приложения из чарта                              |
| `helm.sh/chart`                | Имя и версия чарта                                      |
| `ecpk/instance`                | `global.identity.instance`                              |
| `ecpk/cluster`                 | `global.identity.cluster`                               |
| `ecpk/project`                 | `global.identity.project`                               |

Ресурсы сабчартов несут свои labels (`app: namespace`, `app: waypoint`) и те
же теги `ecpk/*`, так что по тегам находится всё, что создал заказ.

Свои labels и annotations добавляются через `generic.labels` и
`generic.annotations`. Они ложатся на ресурсы самого чарта; у сабчартов свои
`generic` под ключами `waypointNamespace` и `vegNamespace`.

## Секция `mode`

| Значение | Что это                                                            |
|----------|--------------------------------------------------------------------|
| `mesh`   | Ваши сервисы в сетке. Наружу через выход уходят только домены из `serviceEntries[]`. По умолчанию |
| `direct` | Ваши сервисы без сетки. Через выход уходит весь внешний трафик их подсети или помеченных подов |

В режиме direct `waypointNamespace.enabled` должен быть `false`, а
`serviceEntries`, `networkPolicy` и `authorizationPolicy` - пустыми или
выключенными: чарт остановит рендер, если они заполнены.

## Секция `senders`

Ваши сервисы: один существующий namespace на заказ.

| Поле        | Нужно указать                                 | Что это                                                     |
|-------------|-----------------------------------------------|--------------------------------------------------------------|
| `namespace` | да                                            | Namespace, из которого сервисы ходят наружу                  |
| `subnet`    | да в режиме direct с выбором всей подсети     | Подсеть этого namespace, именем: `{проект}-{кластер}-subnet-{назначение}` |

Имя подсети видно в карточке пространства и в самом заказе на него, например
`nbox-dev-subnet-app`.

## Секция `serviceEntries[]`

Только режим mesh. Один элемент - один внешний сервис, к которому ходят ваши
приложения.

| Поле        | Нужно указать            | Что это                                                          |
|-------------|--------------------------|-------------------------------------------------------------------|
| `name`      | да                       | Имя, от 2 до 9 символов. Попадает в имя `ServiceEntry`            |
| `hostname`  | да                       | Домен внешнего сервиса                                            |
| `enabled`   | нет, по умолчанию `true` | При `false` `ServiceEntry` не создаётся                           |

На каждую запись чарт создаёт один `ServiceEntry` в namespace ваших сервисов и
вешает на него два лейбла: `istio.io/use-waypoint` с именем гейтвея и
`istio.io/use-waypoint-namespace` с namespace гейтвея. Этого достаточно:
ztunnel перехватывает трафик приложений к этому домену и туннелирует его в
гейтвей по HBONE, тот выпускает его наружу через выход. Порт всегда 443.

Остальное чарт заполняет сам: сервис считается внешним по отношению к mesh, его
адрес ищется по домену, порт описывается как TLS. `ServiceEntry` виден в своём
namespace и в namespace гейтвея.

## Секция `vpcEgressGateway`

Один выход на заказ.

| Поле          | Нужно указать            | Что это                                              |
|---------------|--------------------------|-------------------------------------------------------|
| `name`        | да                       | Имя, от 2 до 9 символов                               |
| `externalIPs` | да                       | Внешние адреса. Сколько адресов, столько и экземпляров |
| `scope`       | нет, по умолчанию `namespace` | Только direct: `namespace` (вся подсеть) или `label` (поды с меткой) |
| `label`       | нет, по умолчанию `ecpk/egress` | Только direct с `scope: label`: ключ метки на подах |

Что выход захватывает, чарт выводит из режима. В режиме mesh это поды гейтвея в
его namespace. В режиме direct с `scope: namespace` это вся подсеть из
`senders.subnet`; с `scope: label` это поды namespace ваших сервисов, на которых
стоит метка с ключом из `label` и значением, равным имени выхода в кластере
(например `ecpk/egress: ed-dev-veg-nbox-vip`). Правила кластера следят, чтобы
такая метка стояла только там, где выход заказан, и не сочеталась с сеткой.

Параметры VPC (сама VPC, внешняя подсеть `egress-vip`) зашиты в шаблоне и через
значения не настраиваются. Выходы размещаются на мастер-узлах кластера:
ingress-шлюз сервиса работает на воркерах, и делить с ним узел выходы не
должны.

## Секция `networkPolicy`

Только режим mesh. Включается одним флагом.

| Поле          | Нужно указать             | Что это                                                     |
|---------------|---------------------------|--------------------------------------------------------------|
| `enabled`     | нет, по умолчанию `false` | При `true` создаются политики                                |
| `endpoints[]` | да, когда `enabled: true` | Адреса и порты, к которым гейтвею разрешено ходить           |
| `senders`     | нет, по умолчанию `true`  | Правило в namespace ваших сервисов: выход к гейтвею          |

Политика `...-out` в namespace гейтвея разрешает ему исходящий трафик: до istiod
(namespace `istio-system`, порт 15012), до CoreDNS (namespace `kube-system`,
порт 1053 по TCP и UDP) и до каждого адреса из `endpoints[]`. Первые два
зашиты в чарте, без них гейтвей не работает.

Политика `...-in` в namespace гейтвея разрешает входящий трафик на порт 15008
(HBONE, на нём гейтвей принимает туннель от ztunnel) из namespace ваших
сервисов.

Политика `...-senders` в namespace ваших сервисов разрешает всем его подам выход
в namespace гейтвея на порт 15008. Namespace в сетке живёт под правилами по
умолчанию платформы, и без этого правила ztunnel не откроет туннель к гейтвею.
Отключайте его (`senders: false`), только если в namespace ваших сервисов
правил по умолчанию нет: там оно изолировало бы поды вместо того, чтобы их
выпустить.

| Поле                    | Нужно указать | Что это                                             |
|-------------------------|---------------|------------------------------------------------------|
| `endpoints[].address`   | да            | IP внешней точки или подсеть в формате CIDR          |
| `endpoints[].port`      | да            | Порт, на который гейтвей ходит по этому адресу       |

Одиночный IP чарт сам превращает в подсеть на один адрес.

## Секция `authorizationPolicy`

Только режим mesh.

| Поле      | Нужно указать             | Что это                              |
|-----------|---------------------------|---------------------------------------|
| `enabled` | нет, по умолчанию `false` | При `true` создаётся правило доступа  |

Создаётся одно правило `ALLOW` в namespace гейтвея, привязанное к нему через
`targetRefs`. Оно пускает к гейтвею трафик из namespace ваших сервисов и больше
ниоткуда. Задавать в секции больше нечего.

## Секции `waypointNamespace` и `vegNamespace`

Это значения сабчарта `namespace` для двух служебных namespace. Всё, что чарт
фиксирует, уже стоит в его значениях по умолчанию: роль `egress`, уровень Pod
Security (`baseline` у гейтвея, `privileged` у выхода), сетка (всегда у
гейтвея, никогда у выхода), квоты и неизолированная подсеть. Заказ дописывает
три вещи:

| Поле                                   | Нужно указать              | Что это                                        |
|----------------------------------------|----------------------------|-------------------------------------------------|
| `waypointNamespace.enabled`            | `false` в режиме direct    | Создавать ли namespace гейтвея                  |
| `waypointNamespace.waypoint.waypoints` | да в режиме mesh           | Ровно один элемент: сам гейтвей, см. ниже       |
| `*.subnet.enable`, `*.subnet.subnets[].cidrBlock` | когда диапазон зарезервирован | Подсеть namespace                    |

Гейтвей описывается как элемент списка вейпоинтов чарта `waypoint`:

| Поле                | Нужно указать | Что это                                                      |
|---------------------|---------------|---------------------------------------------------------------|
| `name`              | да            | Имя гейтвея, от 2 до 6 символов                               |
| `allowedNamespaces` | да            | Namespace ваших сервисов: без него привязка `ServiceEntry` к гейтвею не действует |
| `hpa`               | нет           | Автомасштабирование: `enabled`, `minReplicas`, `maxReplicas`, `averageUtilization` |
| `resources`         | нет           | Ресурсы контейнера гейтвея                                    |

Список не сливается со значениями по умолчанию: элемент описывается целиком.
Остальные поля сабчартов описаны в чартах `namespace` и `waypoint`.

## Когда рендер останавливается

- не задан `global.identity` или задан `identity` в корне; в тегах недопустимые
  символы, `project` длиннее 9 символов;
- `mode` не `mesh` и не `direct`;
- не задан `senders.namespace` или он совпадает с namespace гейтвея или выхода;
- у выхода не задано имя или список внешних адресов пуст;
- не задано `vegNamespace.namespace.name`, оно совпадает с
  `global.namespacePurpose`, роль namespace выхода не `egress` или у него не
  стоит `serviceMesh.never: true`;
- режим mesh: не задано `global.namespacePurpose`; `waypointNamespace` выключен,
  без сетки или без вейпоинта; задано `waypointNamespace.namespace.name`; в
  списке вейпоинтов не ровно один элемент; namespace ваших сервисов не указан в
  `allowedNamespaces` гейтвея; список внешних сервисов пуст; у внешнего сервиса
  не заданы имя или домен; два внешних сервиса названы одинаково или указывают
  один домен;
- режим direct: `waypointNamespace` включён; заданы внешние сервисы, сетевые
  правила или правило доступа; не задана `senders.subnet` при выборе всей
  подсети; `scope` не `namespace` и не `label`; `label` не похож на ключ метки;
- `networkPolicy.enabled: true`, а список `endpoints[]` пуст или у записи не
  задан адрес либо порт.

Сабчарты `namespace` и `waypoint` добавляют свои проверки: маска подсети,
формат CIDR, квоты.
