# policies

Чарт описывает правила доступа между сервисами в Kubernetes и Istio. Вы
перечисляете в значениях, кто и на какие порты может ходить, а чарт превращает
это в `NetworkPolicy` (сетевой уровень) и `AuthorizationPolicy` (уровень Istio).

## Что создаёт чарт

Значения разбиты на три независимые секции, использовать можно любую или сразу
несколько.

| Секция       | Что создаётся                                            | Когда брать                                                     |
|--------------|----------------------------------------------------------|-----------------------------------------------------------------|
| `policies[]` | `NetworkPolicy` и `AuthorizationPolicy` с зеркалами у второй стороны | Основной случай: описать связь сервиса с соседями целиком |
| `netpol[]`   | только `NetworkPolicy`, без зеркал                       | Нужен контроль сетевого уровня или правило по диапазону адресов  |
| `authzpol[]` | только `AuthorizationPolicy`                             | Нужны правила Istio, а сетевые политики заданы другим способом   |

## Куда ставится релиз

Ресурсы владельца создаются в namespace релиза, поэтому чарт ставится в тот же
namespace, где живёт сам сервис. Namespace второй стороны берётся из правил.

Секция `policies[]` дополнительно создаёт зеркала, чтобы связь заработала без
установки чарта у соседа:

- egress-правило (владелец ходит наружу) добавляет получателю входящую
  `NetworkPolicy` и `AuthorizationPolicy` с principal владельца;
- ingress-правило (к владельцу ходят) добавляет отправителю исходящую
  `NetworkPolicy`.

Зеркала создаются только для правил, где вторая сторона задана namespace (и,
если нужно, селектором подов). Для правил по диапазону адресов и для сырых
селекторов зеркал нет: там нет namespace, в котором их можно было бы создать.

Если несколько правил ссылаются на один и тот же namespace, зеркала сводятся в
один манифест, а порты объединяются. Когда один namespace одновременно и
получатель, и отправитель, селектор подов в обоих правилах должен совпадать,
иначе рендер останавливается с подсказкой.

## Теги окружения и проекта

Секция `identity` задаётся один раз на релиз. Из неё собираются имена ресурсов
и labels, по которым политики потом находятся в кластере.

| Поле                | Что это                                                                                   |
|---------------------|-------------------------------------------------------------------------------------------|
| `identity.instance` | Тег инстанса окружения. Обязателен, значение из таблицы ниже                                |
| `identity.cluster`  | Тег кластера окружения. Обязателен, значение из таблицы ниже                                |
| `identity.project`  | Тег проекта. Обязателен, до 9 символов: строчные латинские буквы, цифры и дефис             |

Дефис в теге проекта не может быть первым или последним символом.

Пара тегов окружения:

| Окружение      | `identity.cluster` | `identity.instance` |
|----------------|--------------------|---------------------|
| Infra-dev-ecpk | `inf`              | `in`                |
| dev-ecpk       | `dev`              | `id`                |
| techsec-dev    | `tco`              | `ed`                |
| dev-common     | `dev`              | `ed`                |
| test-common    | `tst`              | `ed`                |
| global         | `gl`               | `pr`                |
| observability  | `obs`              | `pr`                |
| techsec        | `tcc`              | `pr`                |
| int-common     | `cmi`              | `pr`                |
| ML             | `ml`               | `pr`                |
| ext-common     | `cme`              | `pr`                |

Оба поля описаны в схеме значений перечислением, поэтому в форме портала они
выбираются из списка. Берите значения строкой таблицы: схема проверяет каждое
поле по отдельности и не поймает пару из разных окружений.

## Имена ресурсов

Имя каждого ресурса собирается из пяти частей:

```
{instance}-{cluster}-{kindShort}-{project}-{name}
```

- `instance`, `cluster`, `project` - теги из секции `identity`;
- `kindShort` подставляется по типу ресурса: `np` для `NetworkPolicy`, `ap` для
  `AuthorizationPolicy`;
- `name` - имя элемента секции: от 2 до 6 символов, строчные латинские буквы,
  цифры и дефис.

Пример: `ed-dev-np-nbox-core`. Итоговое имя обрезается до 63 символов. Имя
элемента должно быть уникально в пределах namespace и типа ресурса.

## Labels на ресурсах

На каждый `NetworkPolicy` и `AuthorizationPolicy` проставляется:

| Label                          | Значение                                          |
|--------------------------------|---------------------------------------------------|
| `app`                          | `policies` - имя чарта, не зависит от имени релиза |
| `app.kubernetes.io/name`       | Имя чарта                                          |
| `app.kubernetes.io/instance`   | Имя релиза                                         |
| `app.kubernetes.io/managed-by` | `Helm`                                             |
| `helm.sh/chart`                | Имя и версия чарта                                 |
| `ecpk/instance`                | `identity.instance`, если тег задан                |
| `ecpk/cluster`                 | `identity.cluster`, если тег задан                 |
| `ecpk/project`                 | `identity.project`, если тег задан                 |

Значения `ecpk/*` приводятся к нижнему регистру, то есть совпадают с тем, что
попало в имя ресурса. По ним отбираются все политики окружения или проекта.

Свои labels и annotations добавляются через `generic.labels` и
`generic.annotations`: они попадают на те же ресурсы. Задаются только на весь
релиз сразу, отдельно по ресурсам их не задать.

## Значения по умолчанию

Секция `defaults` задаёт общее для всех правил.

| Поле                         | Что это                                                                          |
|------------------------------|-----------------------------------------------------------------------------------|
| `defaults.trustDomain`       | Istio trust domain, из которого собирается principal. По умолчанию `cluster.local` |
| `defaults.namespaceLabelKey` | Ключ label namespace для селектора. По умолчанию `kubernetes.io/metadata.name`     |
| `defaults.protocol`          | Протокол портов в `NetworkPolicy`. По умолчанию `TCP`                              |

Протокол переопределяется у конкретного порта, например
`ports: [{ port: 1053, protocol: UDP }]`.

## Секция `policies[]`

Один элемент описывает сервис-владелец и его связи.

| Поле             | Нужно указать                | Что это                                                                     |
|------------------|------------------------------|------------------------------------------------------------------------------|
| `name`           | да                           | Имя политики, от 2 до 6 символов. Подставляется в имена ресурсов              |
| `enabled`        | нет, по умолчанию `true`     | При `false` элемент пропускается целиком                                      |
| `serviceAccount` | да, если есть egress-правила | ServiceAccount владельца. Попадает в principal зеркальной `AuthorizationPolicy` |
| `selector`       | да                           | Селектор подов владельца                                                      |
| `ingress[]`      | нет                          | Кто может обращаться к владельцу: `from` и `ports`                            |
| `egress[]`       | нет                          | Куда владелец может обращаться: `to` и `ports`                                |

Вторая сторона в `from` и `to` задаётся одним из способов:

- `namespace` и, при необходимости, `selector` подов. В `from` можно добавить
  `serviceAccount` отправителя: тогда в правило Istio попадёт principal, а без
  него - namespace целиком.
- `ipBlock` с полем `cidr` и необязательным списком `except` - диапазон адресов.
- `namespaceSelector` и `podSelector` в формате Kubernetes - для случаев, когда
  простой формы не хватает.

В egress-правилах `serviceAccount` у второй стороны указывать нельзя: рендер
остановится. ServiceAccount владельца берётся из `serviceAccount` самого
элемента.

Порт записывается объектом: `{ port: 8080 }` берёт протокол из
`defaults.protocol`, `{ port: 8080, protocol: UDP }` задаёт его явно.

## Секция `netpol[]`

Только `NetworkPolicy`, без правил Istio и без зеркал.

| Поле        | Нужно указать            | Что это                                                     |
|-------------|--------------------------|--------------------------------------------------------------|
| `name`      | да                       | Имя, от 2 до 6 символов                                      |
| `enabled`   | нет, по умолчанию `true` | При `false` ресурс не создаётся                              |
| `selector`  | нет                      | Селектор подов. Если не задан, политика действует на весь namespace |
| `ingress[]` | нет                      | Список правил вида `from` и `ports`                          |
| `egress[]`  | нет                      | Список правил вида `to` и `ports`                            |

## Секция `authzpol[]`

Только `AuthorizationPolicy`.

| Поле       | Нужно указать             | Что это                                                       |
|------------|---------------------------|----------------------------------------------------------------|
| `name`     | да                        | Имя, от 2 до 6 символов                                        |
| `enabled`  | нет, по умолчанию `true`  | При `false` ресурс не создаётся                                |
| `action`   | нет, по умолчанию `ALLOW` | `ALLOW`, `DENY`, `AUDIT` или `CUSTOM`                          |
| `selector` | нет                       | К кому применяется. Если не задан, ко всем сервисам namespace  |
| `rules[]`  | да                        | Правила: `from`, `ports` и `when`                              |

Источник в `from` задаётся списком `serviceAccounts` (разворачиваются в
principal), готовыми строками `principals`, диапазонами `ipBlocks` или списком
`namespaces`. В `when` поддерживается `sourceNamespaces`.

## Когда рендер останавливается

Чарт не даёт выпустить политику, которая молча разрешит лишнее, и называет поле,
из-за которого остановился:

- не заданы `identity.instance` или `identity.cluster` либо в них недопустимые
  символы;
- `identity.project` длиннее 9 символов или содержит недопустимые символы;
- имя элемента секции короче 2 или длиннее 6 символов;
- у элемента `policies[]` не задан `selector`;
- есть egress-правило, но у элемента не указан `serviceAccount`;
- в egress-правиле указан `serviceAccount` второй стороны;
- вторая сторона в правиле не описана ни одним из поддерживаемых способов;
- в правиле указан `serviceAccount`, но не указан namespace, к которому он
  относится;
- несколько правил ссылаются на один namespace с разными селекторами подов:
  такие правила нужно развести по отдельным элементам секции.

## Файлы чарта

| Файл                  | Для чего                                                              |
|-----------------------|------------------------------------------------------------------------|
| `values.yaml`         | Значения по умолчанию: теги-заглушки и пустые секции, политик не создаёт |
| `values.minimal.yaml` | Короткий рабочий пример: один сервис, один вход и один выход             |
| `values.full.yaml`    | Полный справочник: все параметры с пояснениями                           |
| `values.schema.json`  | Схема значений: проверка при установке и форма заказа в портале          |
| `view.schema.json`    | Как форма и карта связей выглядят в портале                             |
